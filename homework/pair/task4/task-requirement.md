# 2026秋软件工程第二次结对作业之程序实现

作业提交期限（Deadline）：2026-10-10 23:59:59

## 前情提要

你们的上一次结对作业，各显其能，围绕校园里失物信息分散、群聊消息容易被覆盖、查找不便等现实困扰，进行了分析和梳理，也给出了自己的解决方案。大家采用了墨刀、Penpot等原型设计工具，有的还制作了可交互的HTML原型，从首页的信息展示，到寻物和招领的发布，再到搜索、详情和“我的发布”，把一个生活中的想法逐步变成了可以呈现的产品方案。同时，你们可能也认识到，看上去挺简单的要求或文字描述，要通过原型清楚地表达出来，也需要经过详细的构思、合适的编排和反复的调整。但是，也许因为时间紧迫，也许因为经验不足，原型和需求分析仍然有提升空间。针对我所看过的这几份作业，主要还有以下问题：

1. 有的方案功能铺得比较开，对本次任务的范围把握还不够。第一次作业已经说明，不要求复杂后台、实名认证、即时聊天和地图定位，但有的原型仍然设计了附近地图、站内消息、收藏、浏览记录等多个模块，也有页面列出了“实名认证”。这些功能并不是不能设计，而是需要先想清楚：它们解决了什么必须解决的问题？后续两个人是否有能力和时间实现？尤其是已经注明地图位置、距离只是示意数据的方案，不能因为页面上画出了地图，就认为已经解决了按位置查找的问题。如果时间有限，应该先把发布、搜索、查看详情和信息状态维护做好。
2. 需求分析更多是对题目痛点的整理，缺少实际用户反馈的支撑。大家都提到了信息分散、群聊刷屏、查找困难，但在这几份博客中，我还没有看到具体的用户访谈或试用反馈记录。有的方案甚至提出可以把寻物周期从数天缩短至数小时，这个判断的依据是什么？不妨问问真正丢过校园卡、钥匙的同学，也问问捡到物品却不知道交给谁的同学，他们最难解决的究竟是哪一步。两位同学讨论出了功能列表，并不等于已经验证了用户需求；列出了NABCD模型，也不等于其中的效果已经得到证实。
3. 功能清单写得比较齐全，但流程说明没有完全跟上。有的作业列出了搜索、修改状态和“我的发布”，使用流程却主要停留在“浏览或搜索—查看详情—联系发布者”和“填写信息—发布成功”，对于联系之后如何结束这条信息，没有同样清楚地展开。既然已经设计了“已找到”“已归还”，就应该让人看明白：谁来修改？从哪个入口修改？修改后其他用户在哪里看到结果？这些问题在部分博客中还没有交代清楚。功能名称列在文中，不代表相关流程已经表达完整。
4. 页面设计与实际交互之间，还需要更充分的检查。有同学在总结中提到，透明点击区域虽然绑定了跳转，预览时却不能响应；也有同学提到，后来才补上首页卡片到详情、发布按钮到成功提示的交互。这些问题经过排查得到修正，说明大家确实做了尝试，但也提醒我们，界面画出来和用户能够用起来是两回事。从提交的材料看，部分博客主要展示页面说明和操作步骤，对实际走查结果的展示还不充分。尤其是发布信息不完整、搜索无结果等情况，有些方案已经给出了提示，有些还没有在博客中说明，不能只按一条顺利成功的路线设计产品。
5. 过程记录还不够细致。有一份作业的PSP表中，各项预估耗时与实际耗时完全一致，而正文又记录了页面调整和交互排查，却没有解释这些工作与时间估计的关系。时间相同本身不代表记录有问题，但PSP的作用不只是填写一张表，更是帮助你们发现哪些工作低估了、哪些环节发生了返工。相比之下，有的同学记录了工具学习和页面制作明显超时，并分析了原因，这样的记录才更有助于下一次安排任务。

聊完了上一次的作业，分享了我看完这几份作品后的感受，你们站在产品经理的视角，做出了一次设计。接下来，需要你们站在程序员的角度，给出这个产品核心模块的代码实现。

## 一、结对编程正文

做一个“校园失物招领”吧，你们需要在WEB或APP（二选一）上，让用户能够发布寻物信息和招领信息，集中浏览校园里的失物招领内容，并通过物品名称等关键词进行搜索。用户能够查看物品的详细信息及发布者提供的联系方式，在物品找回或归还后，由发布者将信息标记为“已找到”或“已归还”，减少重复询问和无效联系。

请基于第一次结对作业的原型设计，完成上述核心功能，使“发布信息—浏览或搜索—查看详情—联系发布者—更新状态”的基本流程清晰、可用。本次不要求实现复杂后台管理、实名认证、即时聊天、地图定位等功能。除此之外，请尽情丰富“校园失物招领”的内容吧。

### 1. PSP表格

PSP是卡耐基梅隆大学（CMU）的专家们针对软件工程师所提出的一套模型：Personal Software Process (PSP，个人开发流程，或称个体软件过程)。

一个功能完备的程序不是一蹴而就的。可将一个大任务划分为可操作的小任务，同时最好按照任务难度或紧急程度指定各个任务的完成次序。因此，在动手开发之前，要先估计将在程序各模块开发所需耗费的时间，以及完成整个项目所需的时间，将这个（估计值）记录下来，写成PSP的形式。

PSP的目的是：记录工程师如何实现需求的效率，和我们使用项目管理工具（例如微软的Project Professional，或者禅道等）进行项目进度规划类似。

有关PSP的更多内容，请自行阅读邹欣老师的博客：[工程师的能力评估和发展](https://www.cnblogs.com/xinz/archive/2011/10/22/2220872.html)。

### 3. 单元测试

重点：这是一个对于自学能力/信息搜集能力要求比较大的部分。

请根据自己以往积累的测试经验，在编码完成之后，提交产品之前，设计测试用例，并编写单元测试，对自己的项目进行测试。

首先，至少应采用白盒测试用例设计方法来设计测试用例，其他测试方法不限。其次，要设计至少10个测试用例，确保你的程序能够正确处理各种情况。最后，结合测试评估的要求，对自己的测试设计进行评价，这些测试用例能满足该程序测试的要求吗？

另一个重要的措施是要把单元测试自动化，这样每个人都能很容易地运行它，并且可以使单元测试每天都运行。每个人都可以随时在自己的机器上运行。团队一般是在每日构建中运行单元测试的，这样每个单元测试的错误就能及时被发现并得到修改。

推荐阅读邹欣老师的博客：[关于单元测试和回归测试](https://www.cnblogs.com/xinz/archive/2011/11/20/2255830.html)。
