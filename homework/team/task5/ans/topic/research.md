# 选题 Agent 产品调研

2026 年 11 月 3 日 · 供团队选择研究范围和结课验证方式

我建议换到**项目立项前的选题调研**这个方向，课程里可以叫它“选题 Agent”。一个学生说想做菜谱，一个产品经理说想做售后 Agent，他们面临的其实是同一道选择题。现有方案已经替谁做了哪一步？手里的证据足以让学生投入结课前的五周，让产品团队投入下一个迭代吗？如果还差一条证据，下周最值得找谁、查什么？

产品可以做成一套 **Agent 辅助的模块化调研流程**。团队带着一个问题、几个方向或一包已经查过的资料进来，按需使用机会梳理、先例检索、逐项比较、可行性判断和验证设计。最后留下的是一份能带去开会的立项记录，写清选哪个方向、放下哪些替代方案、依据在哪里、什么发现会让团队改主意。学生和产品负责人对选择负责，教师和商业评审提供质询。

本轮实际核对了本组旧稿、两届公开选题、18 个产品与替代办法，以及电商售后产品的操作文档。下文的两组案例是按资料做的人工比较。产品效果、用户访谈和商业付费意愿属于下一阶段验证项。竞品逐项记录了适用用户、已有能力、采用条件和来源。[作业要求](../../task-requirement.md) · [竞品调研与评估](assets/competitor-research.md)

## 一、把这次换题当作第一份研究材料

按本组转述，老师给的是建设性意见，团队自行决定范围并承担结果。往届出现过相近题材，这一点有公开先例。至于两组是不是在做同一件事，把“菜谱”拆到任务上比争论这个词更清楚。

| 对照材料 | 谁在什么情况下打开软件 | 一次使用实际要做什么 | 哪个结果值得验收 |
| --- | --- | --- | --- |
| 本组原选题，菜谱库 v0.3 | 做饭新手找到一个可借鉴的做法，又想记住自己上次怎么改的 | 收集外部菜谱，整理成个人版本，做后记下调整，下次取回 | 能否找到上次采用的做法和反馈，再按自己的条件使用。[本组旧 PRD 的产品主线](../recipe/prd.md) |
| 2026 年“海底小纵队”膳食搭配智能体系统 | 有自炊条件、希望主动调控饮食的用户要安排餐食 | 根据资料与个人条件计算能量和营养分配，映射到家常菜，并处理饮食限制 | 团队把配餐计算、菜式落地和依据核查列为代表性任务。[同期选题报告的项目概述、任务与验收标准](https://www.cnblogs.com/myuani/p/23426509) |
| 2024 年“银河护胃队”智能健康饮食推荐系统 | 用户拿不定主意吃什么，想结合健康情况和附近可买的食物做选择 | 关联营养资料、健康目标和外卖商品，推荐食谱、附近商家或食物 | 推荐能否对应当前用户和可获得的餐食。这里比较的是该队公布的设计范围。[往届选题报告的项目简介与需求介绍](https://www.cnblogs.com/starryship/p/18496633) |

这三份材料能支持的判断是**同一题材，部分任务重合**。三组都要把饮食信息变成可执行的吃法。后两组在营养目标和饮食推荐上重合得更多，本组旧稿把重点放在同一道菜的个人版本与再次使用。要主张本组“涵盖”同期项目，还得拿出营养目标计算、禁忌处理等对应交付。仅凭范围写得宽，包含关系还立不起来。

学生提交“去年也有人做过”这条线索，系统找出先例原文，把相同用户、相同任务、不同约束分开。评审据此可以追问“能不能展示一次做后调整在下次被正确复用”。团队可以带着这个问题继续做，也可以比较新的选题。老师给出的意见和团队最后承担的决定，各有记录。

拿新方向本身试一次，会得到三个实质不同的候选。**往届选题检索库**把先例尽快找全，现成的搜索与表格就可以先试。**选题调研与复核**接着处理先例到底有多像、缺什么材料、换题后是否回应了上次意见，这是本轮建议优先验证的方向。**行业 Agent 进度观察**还要长期维护版本、执行权限和部署证据，先选一个行业做样板。如果首轮访谈发现大家最大的困难只是找不到往届作业，一份好索引就值得先交付。如果找到了先例仍争论不清楚，才有理由为后面的判断环节投入开发时间。

## 二、谁需要它，谁愿意承担调研成本

| 用户与触发时刻 | 现在常用的办法或可用替代 | 最费判断的地方 | 他愿意拿走的结果 |
| --- | --- | --- | --- |
| 学生团队的项目负责人，在选题、撞题或缩范围时 | 翻课程博客、问学长、让通用模型列点子，在群里讨论 | 能找到同题材，难说明两组在替谁完成哪项任务。还要一起权衡团队能力、剩余工期和能接触到的用户 | 两三个有来历的候选、最近先例、结课前能完成的代表性任务，以及一个本周就能检验的假设 |
| 教师、助教或比赛评委，在一批项目第一次评审或重新答辩时 | 对照作业条目、查看往届报告、逐组提问 | 标题相似时容易先入为主。不同组给的材料详略不一，同一标准很难落到同一种证据上 | 带出处的跨组对照、每组最值得追问的一两项、团队上次收到的意见及本次修改 |
| 产品工作室、小型 B2B 软件团队，在接案、排迭代或申请试点预算时 | PM 查竞品，销售提供客户反馈，研发估工期，负责人在会上作取舍 | 客户说“做个 Agent”，已有系统可能早能完成其中大半。谁真受困、谁能开放数据、谁愿意出预算，常常是三个人 | 可以带去立项会的候选比较，现有替代的动作边界，试点负责人、证据缺口和继续投入的条件 |
| 企业创新或行业研究人员，在定期复查一个业务流程时 | 查供应商资料、做市场地图、维护内部项目组合 | 一个产品能回答、能建议、能经授权改变业务状态，分别代表不同进度。发布公告和客户实际使用也回答不同问题 | 按业务动作展开的能力与证据表，带日期的变化，以及受变化影响的旧结论 |

课程验证先找前两类人，他们最容易带来真题和评语。商业验证优先找**反复接新项目、已有少量客户材料、却还没有专职研究团队的产品负责人**。使用者可能是 PM 或研究员，决定给不给下一轮预算的是负责人。已经把大量客户反馈和路线图沉淀在企业平台中的团队，有充分理由沿用原系统。Service Express 就公开描述了用 Productboard Spark 将市场材料、内部反馈和机会评分放进同一流程。这个案例可以证明类似工作在企业里确实有人做，国内小团队采用哪种工具、愿意付多少钱还要单独验证。[Service Express 的实际工作方式](https://www.productboard.com/customers/service-express/)

## 三、一份调研怎样从头做到可以评审

**手上还没有题目时**，从一次真实经历开始。让学生交一条自己观察到的困难，或让产品经理带来一张近期工单。在“谁在什么时候想完成什么、现有做法为什么卡住”说得清楚之后，才展开两三个应对办法。每个方向都标明来自哪条材料、要改变哪个动作、靠什么判断有用。用户可以同时保留一个普通软件或人工优化方案，用来比较增加 Agent 的收益。

**已经有候选时**，可以直接从先例比较开始。例如把“帮学生评估选题”放进系统，应当找回知网的题目排重、Devpost 的评审设置，还应找回面向企业 PM 的机会评估工具。它们的名字相差很远，争夺的却是同一段工作时间。每个入选先例都应说明重合在哪个动作，差异在哪个条件，原文能证明到哪一步。评审者可以撤下一条弱对照，同时保留撤下的理由。[知网指导教师手册](https://jwc.hntou.edu.cn/sjjx/bylw/202312/P020231226620205001228.pdf) · [Devpost 评审设置](https://help.devpost.team/article/230-how-to-set-up-judging) · [Productboard Spark](https://www.productboard.com/product/spark/)

**到了评审会**，学生看到自己要补哪项依据，老师看到每个候选最值得追问的地方。评审人可以认可结论，也可以注明“现有资料只能支持需求相近，交付是否相同还缺演示”。团队补上演示后，只复核依赖那份材料的判断。下一轮打开同一个选题，能看见上次为何暂缓、谁补了什么、决定为什么改变。商业立项会复用这条流程，把课程评价项换成客户影响、已有替代、接入成本、负责人和试点条件。

## 四、把已有的判断方法拼成可以替换的模块

值得自己做的是把**每一步何时启动、需要什么依据、谁接受结果、出错后退回哪里**说清楚。成熟的检索、研究、评分和协作工具都可以参与。下面是一套建议组合，用户带来的既有材料可以从中途接入。

| 判断环节 | 借什么方法，Agent 做什么 | 固定规则和人负责什么 | 交到下一步的产物 |
| --- | --- | --- | --- |
| 确认目标并找候选 | 借机会解决方案树，把目标、用户困难、候选解法和最冒险的假设拆开。Agent 从经历或工单中提出不同解法，追问最影响选择的歧义 | 用户确认目标、周期、团队能力及可访问的资料。已有候选可直接录入 | 一份约束说明、两三个有来源的方向和共同的替代做法。[Product Talk 的机会解决方案树](https://www.producttalk.org/opportunity-solution-trees/) |
| 找到容易漏掉的替代 | 分别按产品名、用户任务和交付结果检索。Agent 为同义异名的产品换搜索词，也主动找能削弱原想法的先例 | 程序记录检索日期、来源、去重和排除理由。用授权导出、已有书签或搜索服务均可 | 有覆盖范围的先例清单。这里借用 PRISMA 记录纳入与排除依据的做法。[PRISMA 筛选记录](https://www.prisma-statement.org/prisma-2020-flow-diagram) |
| 判断究竟重合在哪里 | 借鉴技术特征对先例的逐项映射。对齐服务对象、触发、输入、关键动作、执行权限、产物和验收方式。Agent 给每条关系配上支持与反对材料 | 程序校验定位和来源标识。人处理冲突，根据证据选择核心任务重合、局部重合、题材相邻或待查 | 一份可以逐行点回原文的对照。名称相近但任务不同的项目能拆开，名称迥异却解决同一问题的产品也能找回来。[Patsnap 的特征与证据映射](https://eureka.patsnap.com/novelty-search) |
| 权衡需求与可行性 | Agent 对照硬条件和候选方案找阻塞，例如依赖不可取得的数据，或普通流程已经能完成目标。商业场景可借 RICE 讨论触达、影响、信心和投入 | 团队确认工期、责任人、估算依据与必须通过的条件。有数据时按公开公式计算，缺数时保留区间或待查。教师使用公布的课程条目 | 可继续、需收窄、先补证或暂缓的建议，附改变建议所需的条件。[Intercom 的 RICE 方法](https://www.intercom.com/blog/rice-simple-prioritization-for-product-managers) |
| 为最关键的未知设计验证 | 借 Test Card 把一个假设写成现实中做得了的试验。Agent 提议找谁、看什么行为、怎样区分两种解释 | 人事先定观察标准、负责人和期限，授权访谈或材料使用。实际观察由参与者完成 | 一张验证卡和回填的位置。一条假设有一次明确的翻案机会。[Strategyzer Test Card](https://strategyzr.s3.amazonaws.com/assets/vpd/resources/the-test-card.pdf) |
| 评审、决定与再评审 | Agent 按课程或商业标准整理争议，提示新材料会影响哪些旧判断 | 软件保存来源版本和评审意见。学生团队或商业负责人签下范围与取舍，教师保留独立评价 | 带版本的决策记录、下一次复核日期、尚待回答的问题。[Devpost 的评审分工](https://help.devpost.team/article/230-how-to-set-up-judging) |

一条交接记录至少要能回答五件事。**正在判断什么，针对哪个候选，依据哪段材料，在什么条件下成立，谁作了决定。** 外部研究工具只返回一个结论时，把它登记成线索，取回原文再进入事实列。团队已有访谈纪要，可以跳过采集模块。替换检索方式时，只要来源和定位能交接，后面的对照与评审仍能继续。负责人补进新工单后，和它有关的判断重新打开，其余历史意见保留原版本。

例如，“甲涵盖乙”是有方向的判断。先列乙承诺的代表性任务，再逐项指出甲在相同输入、权限和约束下能交付什么，并给出依据。两个方案都能解释退款规则，其中一个还能经授权写回订单，就把解释规则记作重合，把写回订单单列。少一项材料就把那一格留作待证。评审人由此能看见究竟是哪一项差异影响立项，也能指出 Agent 把哪两个动作比错了。

判断模块也要经过挑选。以“找先例”为例，把课程搜索、人工书签和现成竞品检索工具接在同一个位置，给它们一个同名异题和一个跨品类替代，看哪条路径能用较少复核时间找对原文。以“比较先例”为例，如果产品页只说“支持退款”，Agent 下一步应查执行条件。如果能定位到只能受理申请，就改写比较结果。如果已经到达约定的来源上限还查不到，就把执行权限列作待证，交给评审者。这样可以单独替换表现差的环节，也能看出哪一步由人做更划算。

本轮原型可以复用通用 Agent 运行时，通过 API 或 SDK 连接团队的软件。检索扩展、语义比较、反例追问和补证选择交给 Agent。查重、权限、定位、指标计算、版本与导出交给普通程序。来源质量和最终投入由人负责。外部工具可以先用匿名导出件或链接接入，后续再选择值得接的 API。n8n 已经公开了“给定公司、检索对手、分项查资料、写入 Notion”的完整模板，正适合作为检索模块或对照方案。[n8n 公开工作流](https://n8n.io/workflows/2354-automate-competitor-research-with-exaai-notion-and-ai-agents)

## 五、把同一套方法带到商业立项会

假设一家做跨境电商软件的工作室接到“做一个能处理退款的售后 Agent”的需求。负责人要决定是否投入下一轮原型预算。以下先例来自实际阅读的操作文档，客户和立项会是场景推演。

| 调研发现 | 文档能支持的判断 | 对选题的影响 |
| --- | --- | --- |
| Shopify 自助退货与 Flow | 商家可以在后台审查退货申请，批准或拒绝。客户从自助入口提出退货时，Flow 可以触发后续工作流 | “接收申请再通知负责人”已有普通流程可以承接，应把它放进基线。[退货申请管理](https://help.shopify.com/en/manual/fulfillment/managing-orders/returns/self-serve-returns/management) · [Flow 触发条件](https://help.shopify.com/en/manual/shopify-flow/reference/triggers/return-requested) |
| Gorgias 的 Shopify 订单动作 | 启用对应动作后，Agent 接到取消请求会检查订单是否尚未履约。满足条件时，文档描述了取消、补库存和全额退款 | “让 Agent 在未履约订单上执行取消并退款”已高度重合。投入之前应解释现有配置在哪种商家条件下还不够用。[订单动作说明](https://docs.gorgias.com/en-US/ai-agent-actions-make-changes-to-shopify-orders-757792) |
| 同一品牌的退货申请入口 | Gorgias 另有按资格窗口受理退货的流程。商家可配置自动回复后由团队审批处理，也可以引导至 Loop Returns 门户 | 受理申请、批准退货、实际退款是三个动作。若研究员把它们写成一句“支持退款”，评审人无法据此选题。[退货入口配置说明](https://docs.gorgias.com/en-US/set-up-a-return-flow-with-order-management-368442) |

这张表会改变立项会上的问题。**方向 A** 是配置已有流程，为客户节省重复建设的费用。**方向 B** 是处理规则例外，归拢订单、承运记录和商家政策，给有权决定退款的人一份可核对的材料。后者目前只是候选。产品经理需要请愿意参与的商家拿几张脱敏例外工单，复原耗时在哪一步，再让客服用现有后台和候选方案各处理一遍。如果现有后台已经够快，或者材料权限拿不到，就应把预算转向配置服务或暂缓开发。

商业价值可以这样核算。按实际工单量估计每月可节省的复核工时，单列接入、维护、研究员校对和错误处理成本，再请预算负责人确认是否值得试点。这里能检查的是已有能力和下一步该花哪一笔验证成本。供应商公开文档能够证明它如何描述产品，实际配置是否适用于某家店，由该店的试用记录补齐。

## 六、产品亮点与竞争压力

| 用户现在要付出的代价 | 项目值得验证的改进 | 用哪个替代方案拆穿这项主张 |
| --- | --- | --- |
| 找到一堆同类名称，还得通读才能知道是否做同一件事 | 每条重合判断显示动作、触发条件和原文位置，同时纳入异名替代与人工方案 | 同样的材料交给通用研究 Agent 和一张好模板，看谁更少把“同类”判成“同题” |
| 收到“重复”“价值不足”等意见后，需要猜评审到底想看什么 | 把意见改写成能回答的质询，允许评审者纠正，并绑定一份会改变结论的材料 | 与飞书表格的逐条评语比较，从收到意见到另一人找到依据需要多久 |
| 商业报告写完便和后续试点脱节，客户补一条证据得重讲背景 | 沿用既有调研记录，让新材料只触发相关判断复核，留下当时为何投、为何停 | 对照 Productboard 或团队原有待办池，检查第二次立项时是否真的愿意回来复用 |

最现实的竞争是**已有工作流加一位认真负责的人**。研究模板可以分模块交付，完整软件的额外价值要靠复核、交接和再次使用体现。若团队只需一次报告，可以选通用调研工具或按次购买。已有厚实客户数据和战略组合的大公司，原生平台的上下文优势很强。我们优先验证的是从少量材料起步、多人在短周期内做选择的小团队。[竞品评估及五条同题对照路径](assets/competitor-research.md)

## 七、从一个选题扩展到一个领域的 Agent 化进度

这个扩展复用的是“逐动作找证据”。先给领域画出一条具体业务流程，再对每个动作分别记录**工具能读什么、能建议什么、能写入什么、谁审批、失败由谁接手**。退款案例已经提供了第一行可用样本。下次检查时，补记产品版本、证据日期和权限变化，就能说明这条流程往前走了哪一步。

| 想回答的问题 | 合适的证据和分母 | 对外可以写到什么程度 |
| --- | --- | --- |
| 已经有哪些能力供应 | 带日期的帮助文档、接口、演示。分母为本次列明的产品样本与业务动作 | 写“在所查产品中，某一动作已公开支持”，列出地区、权限、配置等已知条件 |
| 能否稳定完成任务 | 可复现试用、固定任务集、失败记录，检查最终业务状态。分母为实际运行的任务次数 | 写“在某组条件下完成多少次”，并记录人工接管。τ-bench 将最终数据库状态与目标状态比对，提供了可借的方法。[τ-bench 原始论文](https://arxiv.org/abs/2406.12045) |
| 是否已在组织里采用并创造收益 | 具名部署材料、授权日志或调查，注明样本如何取得、时间和业务量。分母为实际观察的商家、流程或工单 | 区分单一客户案例、平台样本与行业渗透率。Anthropic 的早期经济指数就说明了其 Claude.ai 会话样本的范围和选择偏差。[Economic Index 方法与局限](https://www.anthropic.com/research/the-anthropic-economic-index) |

以后换到另一个领域，先换业务动作清单、评审人和可信来源，再复用检索、证据映射与更新模块。首轮以一个商业垂直流程做样板。若第二个领域每增加一行都需要重写整套判断方法，就应重新估计“适用于任意领域”这项设想的成本。

## 八、下一轮真正要找谁、带什么来

第一批建议招募 3 位学生团队负责人、2 位有项目评审经验的教师或助教、3 位近期实际选过项目的产品或工作室负责人。学生覆盖未定题、被提示重合和改过题三种经历。商业参与者应能带来一次真实选择，包括搁置或放弃的项目。这些是招募目标，当前的用户证据来自课程事件、公开案例和操作文档。

请每人用原来的方式复原上一次决定。记录最初的两三个候选、引用过的资料、被排除的方案、谁提出异议、哪条新信息改变了范围，以及实际耗时。把同一组匿名材料交给另一位参与者，让他指出最关键的重合并找到原文。若问题集中在招不到用户、拿不到授权或团队无人拍板，就把真正的阻塞写回研究，不把它算成 Agent 可以消除的工时。

商业访谈还要追到预算。现在谁维护竞品表，这类决定一个季度发生几次，已有何种工具和数据授权，下一次愿不愿意拿真实简报做试点，愿意替换哪笔开支？一次使用以复核用时和错误衡量，连续两次真实立项才观察复用意愿。学生愿意试一个免费工具，不能代替企业的付费证据。

## 九、剩余五周怎样交出可检查的软件

课程项目共八周。前两周用于选题，团队当时按剩余六周估算工作量。截至 2026 年 11 月 3 日，距结课还剩五周，下表从本次调整起算。课程演示围绕一次选题和一次改题，商业演示围绕一条售后流程和一次范围收窄。两条路径共用同一套来源、比较、人工意见与版本机制。首期支持粘贴简报、文段或来源链接，使用限定资料库检索，来源读取失败时可补带定位的人工摘录。完整互联网爬取、企业系统批量接入和全行业持续监测各自需要单独验证投入。

| 周次 | 要完成的工作 | 能拿出来检查的产物 |
| --- | --- | --- |
| 剩余第 1 周 | 招募参与者，用真实材料和表格走通一次评审。对齐重合判断，分开调试与留出题包 | 访谈或观察记录、人工基线、可定位的材料、冻结的评价规则 |
| 剩余第 2 周 | 用 API 或 SDK 接入 Agent，打通从提交简报到查先例、逐项比较和补证的操作流程 | 可操作的首版页面，两项以上替代、逐项依据及一个待验证问题 |
| 剩余第 3 周 | 接入人工审阅与版本记录，走通两轮课程评审和商业样例，验证检索来源可替换 | 两种场景的前后版本、修正理由和异常恢复记录 |
| 剩余第 4 周 | 对冻结题包做同题对照，由两名评审独立核查。邀请使用者完成交接任务 | 关键误判、错引、复核耗时、费用及原始计数 |
| 剩余第 5 周 | 修复阻断问题，上线测试版本，备齐公开样例、访问方式与答辩材料 | 老师或助教能从在线入口独立完成提交、核对、批注、修订和导出。[课程交付要求](../../task-requirement.md) |

### 建议的结课验收口径

**交付检查。** 检查人从演示网址进入一个样例，也能自行输入候选。前台能提交材料、展开先例、查看引文、采纳或修正判断、保存第二版。后台实际通过 API 或 SDK 调用模型和检索工具，留有运行记录、来源版本、结果和失败状态。换一条检索路径，原有对照仍可人工复核。教师看到提交给他的版本，企业演示使用授权或公开材料。现场各演示一次来源失效和一次人工纠错，刷新后能找回原判断与修改理由。

**定制效果。** 建议锁定 16 个留出题包，课程与商业各 8 包。12 包预先标注至少一个必须找回的对照，4 包故意缺少足以定性的材料。覆盖名称相近而任务不同、任务相同而品类不同、范围包含、已有普通工具、过期资料及来源冲突。前文已讲解的样例用于调试或演示，另选材料作为留出题。两位评审先独立标注关键先例、关系、证据位置和可接受的下一步，有分歧的案例保留两方理由，再定参考口径。

| 检查什么 | 口径和建议目标 |
| --- | --- |
| 找回决定性的先例 | 看每包最先给出的 3 个对照，12 个有关键先例的题包中至少 10 包命中。关系判断另列混淆表，尤其点名把局部重合判成全面重复的次数 |
| 引用是否真正支持判断 | 在决策性断言中抽核 40 条，逐条回到原文检查主体、动作和条件，建议至少 36 条获支持。凭空捏造的来源为 0。链接可打开单独计数 |
| 何时该让人补证 | 4 个证据不足的题包都指出具体缺项和补证动作。给其中一包加入能改变结论的材料，检查新结论、人工意见与旧版本能否一并回查 |
| 模块是否带来增益 | 通用 Agent 和本组方案拿到同一模型、原始材料、搜索权限、评审标准、输出模板、预算和时间。前者自行组织调研，后者调用本组判断模块。再选 6 个题包由人用表格完成。隐藏输出来自哪种方案，随机展示顺序，记录关键误判、手工修正、复核用时和调用费用 |
| 是否值得做成独立软件 | 把相同模块产物也交给通用客户端或飞书表格，测第二人找到原文、修改判断并交接给下一人的全程。试定目标为同题复核用时中位数减少 20%，且关键误判不增加。报告逐例耗时及适用场景 |

这些数量与阈值是团队讨论用的验收建议。小样本先用于定位失败。若通用 Agent 加上同一套模板已经能达到相同效果，就把通过验证的判断环节交付成可复用模块。若优势只出现在教学评审，商业部分继续观察下一次真实立项是否复用，以及预算负责人愿意为哪一步付费。
