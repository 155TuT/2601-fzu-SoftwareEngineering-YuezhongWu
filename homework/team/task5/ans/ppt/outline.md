# 菜谱 Agent

你所热爱的就是软件工程
**菜谱管理软件** 选题答辩

---

## 横向调研

- 传统菜谱：厨房环境中书本不便保存，改动时便签易脱落、涂抹可读性低
- 传统厨电厂商：配套软件体验依赖设备联动，并不专注于提供普适解决方案
- 真正竞品：
  - Samsung Food、Paprika 3 等食谱软件（深耕食谱领域）
  - Notion、Obsidian 等笔记软件（轻量、高度自定义）
  - 健身类、育儿类、养生/康复类食谱软件（面向特定人群）
  - ...

记一道菜很简单，难的是修改、管理、复用
接入 Agent，做**真正懂你**的纯本地泛用管理方案

---

## 选题价值

真正的**懂**？收藏后，无需**解释**：

- 我到底爱吃什么？-- 从收藏的菜谱和调味料微调出发，建立个人口味模型
- 打算做给谁吃？有谁爱吃？-- 通讯录式存放身边人口味，众口不再难调
- 接下来吃什么？-- 下顿/明天/下周计划，口味模型在实际验证中微调
- 备菜/做菜规划/洗碗、恋人/家庭、生病/健身/育儿忌口 -- 全链路、全角色覆盖

Agent 提供感知、帮助建模、做出细粒度微调：做你**懒得做**的事

## 用户与场景

先服务经常**收藏、做饭、改做法**的人

- 收藏时，保存来源和自己的标签
- 开饭前，按食材和口味选一道菜
- 做完后，记下“下次少放酱油”

下一次打开，找回**自己的做法**

## 首期功能

| 使用环节 | 移动端完成的操作 | 留下什么 |
| :--- | :--- | :--- |
| 收集 | 手工录入、粘贴文字、支持网页导入 | 来源与可校对草稿 |
| 管理 | 搜索、分类、标签、版本比较 | 常用做法与个人改动 |
| 选择 | 确认偏好、请求推荐、调整一道菜 | 有依据的候选和建议 |
| 复用 | 记录反馈、保存新版本、备份恢复 | 下一次可用的经验 |

**收藏进来，整理好，做过之后还能复用**

## 领域知识与 Agent 定制

Agent 结合**菜谱、口味和使用记录**处理具体任务

| 领域资料 | 来源 | 如何使用 |
| :--- | :--- | :--- |
| 菜谱结构 | 用户原文、Schema.org Recipe 字段 | 提取配料与步骤，保留原文依据 |
| 食材与用量 | 团队整理的食材别名、单位规则 | 检索同名食材，按明确份量换算 |
| 口味与反馈 | 用户确认的偏好、实际使用反馈 | 区分长期口味、单菜评价和本次要求 |

App 负责检索、计算和保存；Agent 则负责理解材料、提出建议和解释理由

<!--
第 6 页，用时 65 秒，累计 04:35。

领域定制的重点，是把资料结构和处理规则放进每次任务。菜谱字段参照 Schema.org Recipe，原文来自用户选入的材料。食材别名和单位规则服务于检索与换算。偏好则结合用户确认和实际反馈，并记录适用范围。工作流先从本地取资料，再调用模型，按需要执行领域工具，最后校验结果并交给用户确认。数值换算由程序完成，模型处理语义理解和解释。这些规则共同组成我们对通用模型的定制。

依据：../prd.md 第 7.4 节。字段参考：https://schema.org/Recipe。
-->

## 代表性任务

设计案例：**改成三人份，清淡一些**

| 用户提供的材料 | 工作流的处理要求 |
| :--- | :--- |
| 原菜谱为 2 人份，某配料 200 克，盐适量 | 程序换算为 300 克，“盐适量”保留原表达 |
| 收藏备注写着“这道辣菜是替朋友存的” | 关联收藏用途，长期口味由本人确认 |
| 做完记录“这道菜下次少放酱油” | 反馈关联具体版本，下次复做时提示 |
| 用户采纳配料与步骤的调整建议 | 保存个人版本，保留来源和修改记录 |

<!--
第 7 页，用时 70 秒，累计 05:45。

用这组设计案例看各部分怎样配合。两人份变成三人份，明确的二百克可以换算为三百克，“适量”继续保留。模型结合清淡要求提出调整，并检查相关步骤。另一条收藏备注说明菜谱是替朋友保存的，工作流据此区分收藏特征和本人偏好。做完之后，“少放酱油”先作为这道菜的反馈。用户确认调整后保存新版本，原文和这次改动都有记录。比较定制效果时，我们会检查这些判断和关联是否正确。

## 移动端架构

| 位置 | 职责 |
| :--- | :--- |
| 手机界面 | 导入校对、检索、版本比较、偏好确认和反馈 |
| 手机本地业务与存储 | 保存菜谱、标签、偏好、版本和任务进度 |
| 端内工作流与领域工具 | 读取资料、计算、调用 API、校验结果并确认写入 |
| 远程模型 API | 接收本次任务所需上下文，返回结构化建议 |

离线时可管理本地已有资料，联网时再按队列顺序接续智能分析

<!--

## 手机里的日常体验

- **改动看得清**：逐项比较原文、个人版本和调整建议
- **口味自己定**：确认后复用，随时修改与撤销
- **中断能继续**：按已保存进度恢复草稿和任务
- **资料能带走**：手机内导出备份，在新手机恢复

保存、修改、恢复，都在日常使用的手机上完成

<!--
第 9 页，用时 45 秒，累计 07:25。

手机体验要覆盖完整的使用过程。比较版本时按配料和步骤展开差异，用户决定采用哪些改法。长期偏好经过确认，也可以随时撤销。切换应用或断网后，以本地保存的进度恢复，尚未确认结果的 API 请求由用户决定是否重试。换手机时可以导出和恢复备份。验收会用锁屏、断网、应用重开和备份恢复这些真实操作来检查设计。

## 下一步计划

- **行为访谈**：邀请 8~12 个日常做饭的人，观察菜谱收藏、修改和复做的过程
- **技术选型**：比较双平台原生与跨平台方案，跑通手机 API 最小流程
- **开发与测试**：完成菜谱库和领域工作流，开展真机测试
- **效果与发布**：完成基线对照，找人试用，提供访问地址、安装和测试方式

> 后续按使用反馈拓展亲友口味、排餐、PC 端与跨设备同步
