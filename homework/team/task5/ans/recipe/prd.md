## 一、产品定位：做更懂你的菜谱小助手

**帮助刚开始独立做饭、仍需参照菜谱的人，把找到的菜谱整理成适合自己的做法，并在下一次做饭时用上自己的经验。**

产品主线是：**收进来 → 改成自己的做法 → 做后记一句 → 下次直接复用。** 第一次使用，把零散材料变成可核对的做法；再次使用，找回上次的版本和经验。推荐、分类和偏好都服务于这条主线。

产品采用 Android、iOS 手机 App，**移动端独立完成核心功能，本地存储资料、运行工作流，通过 API 调用模型**。双平台原生与跨平台方案在 M0 调研后选择，PC 作为可选扩展。

## 二、目标用户与需求证据

### 2.1 优先服务谁

| 用户 | 具体处境与任务 | 首期关系 |
| --- | --- | --- |
| 刚开始独立生活、做饭经验较少的人 | 从图文、聊天或短视频中找做法；依赖步骤获得把握，遇到口味或份量变化时需要帮助 | 核心用户，重点验证收集、调整和复做 |
| 家庭中偶尔做饭的人 | 希望照着可靠步骤完成一道菜，并留下适合家人的改法 | 次要用户，使用同一套核心流程 |

首轮招募至少 8 位真实参与者，其中至少 6 位符合核心用户条件、至少 2 位属于次要用户，分别归组。入组依据是近一个月参照菜谱做过菜，并能展示一次实际使用的材料、收藏或修改记录。年龄与职业用于描述样本，招募以行为为准。

### 2.2 如何补齐真实需求

请参与者用现有方法还原“找到菜谱—准备做—改动—下次找回”。重点观察为什么收藏、是否做过、哪里费时、改动如何保存、下次重复输入了什么，以及愿意花多少时间校对和反馈。保留匿名原话、获准材料和操作记录，将团队解释单列。

访谈输出“行为证据—问题原因—对应需求”，据困难的频率与影响调整优先级；同一批参与者可继续参加两轮试用。

### 3.2 从问题追到原因

将改进方向收拢为以下三条问题链。导入限制已有公开依据，其余痛点及原因由访谈和同任务实测验证。

| 用户卡在哪里 | 需要核实的原因 | 产品对应处理 | 如何验证 |
| --- | --- | --- | --- |
| 收藏了做法，准备做时仍要重新抄写、拼凑 | 来源分散在截图、口述文字和链接中，关键用量或步骤缺失 | 多种材料汇入同一校对流程，保留原文与缺项 | 导入到保存的时间、补填次数、关键字段错误 |
| 想少辣、换材料或改人数，却拿不准该怎么改 | 通用菜谱与个人情况有差距，新手难以判断配料和步骤的关联 | 结合已确认口味和本次要求生成成组改动，逐项比较后保存 | 调整依据、配料与步骤一致性、用户纠正及试做反馈 |
| 下次选菜又从头搜索、解释口味，忘了上次改法 | 收藏、个人版本和反馈分散，长期偏好与本次条件混在一起 | 从个人库找回做法，复用有效偏好和对应反馈，本次只补变化 | 找回耗时、重复输入量、依据与范围是否正确、再次使用意愿 |

## 四、产品亮点与持续使用价值

1. **把收集变轻。** 粘贴一段口语记录、一个受支持链接，或选择一张清晰菜谱截图，得到带来源和缺项的草稿。用户在原文旁完成校对。
2. **把做法变成自己的。** 依据口味和本次要求，联动调整配料与步骤，展示改动原因，保留原版和个人版本。
3. **让上次经验进入下次使用。** 做后记一句，系统区分单菜经验和长期偏好；再次打开、调整或选菜时带回适用信息，用户随时纠正。

通用模型提供理解和建议，软件负责读取上下文、比较版本、保存结果和带回经验。用户省下的是查找资料、重复说明和手工整理结果的步骤。结课分别检验领域定制的质量与完整软件的使用成本（第 7.8 节），调整是否合口味由真实试做反馈补充。

基础管理免费，资料保存在手机并可导出，代码与领域规则开源。联网模型的费用、测试额度和数据发送范围在接入时说明。长期价值是逐渐积累自己的家常做法和做饭经历，课程先验证两轮使用中的复用效果。

## 五、用一条完整任务组织体验

以下是设计案例，实际测试采用参与者自己的材料。用户刚开始独立做饭，保存了一张番茄炒蛋截图，希望按两人份做得少甜一点。做完记下“这次偏咸，下次少放酱油”，几天后再次打开这道菜。

| 阶段 | 用户的最少操作 | 软件完成的工作 | 可见结果 |
| --- | --- | --- | --- |
| 开始 | 选择导入材料，或打开内置家常菜 | 提供带来源的基础做法；空库有可直接浏览的入口 | 一份可读、可校对的菜谱 |
| 收进来 | 查看缺项并确认 | 识别配料与步骤，定位原文，保存来源 | 原始做法和个人库条目 |
| 改成自己的 | 点“少甜一点”“改人数”等入口，按需补一句 | 读取有效偏好与所选版本，生成配料和步骤差异 | 带原因的调整预览，确认后成为个人版本 |
| 做后记一句 | 标记做过并保存反馈 | 关联当次版本，按需分析反馈范围 | 单菜记录；长期偏好经确认生效 |
| 下次复用 | 再次打开菜谱或点“按我的口味推荐” | 找回默认版本、上次反馈与有效偏好，本次只补变化 | 可追溯的做法或 1—3 个候选 |

这些环节各有入口，用户完成当前请求后即可结束。已有偏好自动读取，食材、人数和时间按本次需要补充；空库入口和示例要求见第 7.2 节。

### 7.2 页面与交互

主导航采用“菜谱库、推荐、我的偏好、设置”。菜谱库首页突出“收进来”和“继续上次”，导入入口常驻；调整、版本和反馈围绕同一道菜展开。待校对、待确认、连接失败与保存成功均显示明确状态。

| 页面 | 主要信息与动作 | 手机交互 |
| --- | --- | --- |
| 菜谱库 | 搜索、分类、最近使用、导入、自写录入和示例列表 | 常用入口便于单手触达，支持文字、链接和截图 |
| 导入校对 | 原始资料、结构化字段、缺项、来源位置、保存草稿 | 按字段展开对应原文，逐项校对并保存进度 |
| 菜谱详情 | 当前版本、配料、步骤、来源、历史版本、调整与反馈 | 按配料和步骤展示前后差异，在详情中完成比较与采纳 |
| 推荐 | 快捷条件、候选、理由、使用的偏好、需核对项 | 可直接按有效偏好开始；默认展示 1—3 个候选，按需补充本次变化 |
| 我的偏好 | 有效偏好、待确认候选、证据、范围、修改与撤销 | 先展示判断与范围，展开后查看依据并纠正 |
| 设置与任务记录 | 当前资料库、API 配置、数据导出恢复、任务进度与失败原因 | 手机内完成连接测试、文件选择、备份恢复和任务续接 |

空库提供“导入菜谱”“自己写一道”和“浏览示例”。用户可先使用手工管理，再配置智能功能。至少 5 份示例随 App 提供，由团队自写或取得使用授权，标注来源并由用户选择加入个人库。

### 7.3 功能需求

#### F01：建立手机资料库与配置 API

首次打开 App 时创建手机本地资料库，即可录入、检索和整理菜谱。设置页分别显示资料库状态与 API 连接状态，并提供存储用量和最近备份时间。

课程试用提供服务地址、受限测试凭据和额度；用户也可在设置中填写自己的服务、模型与认证信息。M0 冻结首期服务、默认接入方式和凭据发放规则，团队共享密钥通过托管网关使用。

测试连接采用示例输入，检查结构化结果、截图识别和端内工具调用，返回结果与失败原因。安装、接入和业务操作分别计时。

调用前展示服务提供方与本次发送的资料范围，凭据在界面上脱敏。更换接入配置后，已保存资料继续可用；凭据存储与网关职责见第 7.5 节。

#### F02：导入、校对与保存来源

以下输入统一进入“草稿—校对—保存”流程。

| 输入 | 首期范围 | 保存与失败处理 |
| --- | --- | --- |
| 手工与粘贴文字 | 最多 10,000 字符，包含聊天或口述转写后的文字 | 保留原话，将省略、模糊用量和缺失步骤标为待核对 |
| 菜谱截图 | 单张 JPEG／PNG、最多 5 MiB；清晰可读、以一道菜为主的中文印刷文字 | 原图保存在手机内，识别结果关联图中位置；模糊、裁切或多菜内容提示分开处理，保留原图和草稿 |
| 受支持网页 | 公开静态 HTML，含单个 Schema.org Recipe JSON-LD 对象，响应最多 2 MiB | 手机获取并保留链接与快照；登录或结构不支持时提供文字／截图入口 |

截图识别采用多模态模型或 OCR 配合模型整理，M0 以真机原型选定路径。图片发送纳入任务授权；超限文件保留名称与重选入口。

导入后生成草稿，展示标题、配料、步骤、份量、时间、原始资料和缺项。字段区分“来源内容”“用户补充”“模型建议”，关键字段能够定位到文字片段或原图区域。网页元数据与可见原文冲突时列出差异，由用户校对。

只有标题时可以保存待补充草稿；用户确认配料与步骤后转为已入库。用量、份量和时间缺失可保持“未知”，并标记资料完整度。“适量”“一把”等保留原始表达。重复链接或相同内容给出已有条目，用户可以打开已有菜谱或另存。

原始资料保存为来源快照，草稿与校对进度随时保存。离线时先收存支持范围内的文字、图片和链接，联网后继续获取或识别；识别失败可对照来源手工补充。

#### F03：检索、分类与维护个人版本

用户可按名称、配料、标签和来源关键词搜索，并组合分类筛选。普通检索由本地程序完成，已核对的别名用于扩展查找，原料名称及生熟、干湿等状态分别保留。草稿与已入库菜谱分别显示；资料不完整的条目带缺项标记。

菜谱内容修改后新增版本，保留修改说明、时间和前一版本。用户可比较配料与步骤差异，并指定日常查看的默认版本。恢复旧做法通过将旧版本设为默认完成，后续版本仍可查阅。分类和标签属于菜谱的管理信息，可直接编辑。

搜索结果打开当前默认版本，历史反馈继续指向当时使用的版本。

#### F04：记录、分析与确认偏好

用户按需填写口味和避开的食材，点击保存即确认。长期偏好与本次条件使用独立字段；已有有效偏好自动用于推荐和调整，界面提供依据与修改入口。

用户选择菜谱与反馈范围后发起分析，Agent 返回“判断、依据、适用范围、冲突或疑点”。用户可确认、修改或忽略候选。菜谱使用辣椒、用户收藏过它、用户确认喜欢辣味，分别属于材料特征、收藏行为和有效偏好。

每条偏好记录类型、范围、证据、确认时间和有效状态。范围包含“当前请求”“某道菜”“长期个人偏好”。同一范围内发生冲突时展示两条依据，由用户选择或修正。

撤销后立即使偏好退出后续分析、检索和推荐。用户忽略或撤销的候选，在依据没有变化时保持原决定。已有推荐保留历史记录，并标记对应依据已失效；再次请求时重新读取有效偏好。

#### F05：从个人库推荐菜谱

用户点击“按我的口味推荐”，或补充食材、人数、时间等本次条件。默认检索个人库，示例库经用户选择后参与；手机程序检索并检查限制，模型解释排序。

展示 1—3 个实际可用候选，附版本、依据、推荐原因和需核对项。候选不足时说明原因，提供补充条件、浏览个人库或选用示例的入口。

明确的食材限制优先于口味偏好。本次口味要求可覆盖长期口味倾向；与明确限制冲突时先请用户澄清。时间或配料信息未知的菜谱进入“需核对”区域，补齐信息后再判断是否满足条件。

“最近没做过”依据用户明确记录的做饭历史判断，缺少记录时显示“暂无做饭记录”。推荐记录保存所用版本和偏好依据；用户可以查看、纠正理由，也可以直接放弃本次结果。

#### F06：调整一道菜并比较版本

用户在详情中点选改口味、换材料或调整份量，按需补一句要求。系统读取选中版本、适用偏好、单菜反馈和本次条件，返回配料与步骤变化、原因及待核对项。材料替换须同步检查相关步骤，食材限制沿用 F05 的规则。

确定的份量计算交给程序。例如原份量为 2 人、某配料 200 克，调整为 3 人时得到 300 克；“盐适量”“一把”等保留原表达。换算需有明确数量、单位和份量基准；体积与质量互换还需对应食材的密度依据。缺少依据时沿用原单位，分数个数、未知份量和烹调时间列为核对项。

用户可保留原版、保存为个人版本，或选择仅本次试做。试做版本供反馈引用，默认版本保持原选择。采纳前按第 7.6 节校验依据，再将配料与步骤变化作为一组保存。

#### F07：记录使用反馈并复用经验

反馈入口关联具体版本，提供“做过了”、口味标签和一句话记录。保存即记为单菜反馈，用户可稍后补充或主动发起偏好分析；离线记录同样可用。做饭历史以用户标记为准，浏览与收藏分别记录。

“这道菜下次少放酱油”随该菜谱再次展示；“今天想清淡一点”用于当前请求；长期口味判断按 F04 确认后生效。查看或调整菜谱时带回对应反馈。

编辑或删除反馈后，重新核对关联偏好的依据：以它为唯一依据的偏好转为待复核，其余记录保留独立有效依据并更新引用。用户直接填写的偏好以自身确认记录为依据。

#### F08：导出、恢复与删除数据

备份通过手机系统文件入口导出和选择，使用 ZIP 包保存带格式版本号的 JSON、来源图片与附件校验信息。范围为菜谱、版本、标签、反馈、偏好及对象关系；密钥、访问凭据和临时模型上下文排除在备份之外。

首期通过新建空资料库恢复，Android 与 iOS 使用同一备份格式。恢复前校验格式、引用关系、数量与附件完整性，限定解包路径和大小，展示预览；用户确认后整批写入，成功后切换资料库，失败时回滚。导入的有效长期偏好先标为待复核，确认后启用。取消文件选择、文件损坏或空间不足时，保留原资料库并给出处理入口。

备份以文件成功写出为完成，设置页更新成功时间。用户将备份保存到应用之外的位置，用于卸载、清除数据或更换设备后的恢复。

删除菜谱时展示将移除的来源、版本、反馈及受影响的偏好，确认后清理对应内容、检索条目与缓存。其他记录的引用显示“资料已删除”，历史运行日志同步移除相关原文与个人内容。整库删除清理该资料库及其衍生数据。用户自行导出的备份由用户管理，删除提示中说明这一范围。

#### F09：离线使用与本地状态一致性

普通查看、录入、检索、编辑、分类、反馈、偏好管理与本机备份恢复直接操作本地数据，离线可用。历史推荐和调整结果可查看，采纳仍须校验版本与依据。

网页获取和模型调用需要联网。中断时保存输入、已有结果和任务阶段，联网后由用户继续或重试，恢复规则见 F10。

同一 App 的页面、任务和待确认建议共享一套资料版本。提交时携带对象修订号；旧页面或旧建议发生冲突时，保留输入并展示最新内容。切换页面后读取当前状态，草稿按已保存进度恢复。

#### F10：任务状态、取消与失败恢复

工作流按第 7.6 节状态表运行，阶段、输入版本、草稿、请求标识和取消状态保存在手机。分析或推荐交付结果后即可结束；入库、采纳改动和生效长期偏好时等待用户确认。

切换应用、锁屏或系统终止进程时，以最近成功保存的检查点恢复。回到 App 后核对任务与请求状态，再继续未完成步骤。后台持续执行能力按目标系统实测，核心流程以“保存进度—重新打开—继续处理”验收。远程请求结果暂时无法确认时，先标明状态；接口支持查询则尝试取回结果，否则由用户决定是否重新调用，并提示可能重复计费。

初始运行上限为每次任务 3 次远程模型／识别调用、8 次领域工具调用、120 秒累计执行时间，等待用户输入与任务暂停的时间另计。恢复沿用原任务的调用计数和预算；重新调用计入次数。上限在设置和任务记录中可见，测试前冻结。达到上限后返回已有结果与原因。

模型超时、结构错误、工具失败和用户取消均在草稿阶段结束；正式菜谱、版本和长期偏好通过用户确认后的本地事务写入。重复点击确认或重试同一保存请求，使用同一操作标识返回原结果。任务取消状态在 App 重开后继续生效，迟到结果按取消记录丢弃。

### 7.4 领域知识、工具与工作流

#### 领域知识来源

| 领域知识 | 依据与整理方式 | 工作流中的规则 | 对应检查 |
| --- | --- | --- | --- |
| 来源与菜谱结构 | 用户材料、[Schema.org Recipe](https://schema.org/Recipe)；冻结本版字段 | 配料、步骤、份量、准备与烹调时间映射到内部结构，关联原文或图片位置 | D01、A03、A04、A24：来源可回查，缺项与冲突进入校对 |
| 食材名称与状态 | 团队别名表；参考 [FAO/INFOODS 食品匹配指南 1.2](https://www.fao.org/fileadmin/templates/food_composition/documents/Nutrition_assessment/INFOODSGuidelinesforFoodMatching_version_1_2.pdf)中的食品识别维度 | 别名服务于检索；生熟、干湿和加工状态随条目保留 | A05、A08：同名关联可解释，状态变化进入核对 |
| 数量、单位与份量 | 团队换算表、[FAO/INFOODS 密度数据库 2.0](https://www.fao.org/food-composition/tables-and-databases/detail/%28global--2012%29-fao-infoods-density-database---version-2/en) | 明确数量按比例计算，跨单位换算保存依据，语义用量沿用原文 | D03、A11：确定数量正确，原始表达和换算依据可核对 |
| 口味与反馈范围 | 用自写案例和获准访谈材料建立标注集 | 区分材料特征、单菜反馈、临时条件和长期偏好，候选附证据与确认状态 | D02、A06、A07、A26：替朋友收藏与本人喜好分别处理 |
| 配料与步骤关联 | [SHARE，EMNLP 2022](https://aclanthology.org/2022.emnlp-main.761/)将配料替换与步骤生成关联处理 | 改配料后重查相关步骤，成组展示差异 | A12：替换材料后核对相关步骤、原因与待确认项 |
| 用户明确限制 | 用户确认的食材限制及当前请求 | 候选按已知成分区分满足、冲突与未知；包装配料和加工条件提示核对 | A08：限制冲突过滤，资料缺失进入需核对区域 |

团队将资料整理为字段表、别名／单位表、范围标注案例和步骤检查项，记录版本、来源、适用条件、示例及复核人；应用效果由冻结任务与真实试做检验。

#### 软件、Agent 与用户的分工

| 工作流 | 输入与触发 | Agent 处理 | 程序处理与确认结果 |
| --- | --- | --- | --- |
| 导入整理 | 用户提交文字、截图或网页 | 识别文字、理解口语表述、识别缺项和提出分类 | 保存原始材料、校验字段和位置；用户校对后入库 |
| 偏好分析 | 用户选择材料并请求分析 | 提出有依据的候选、解释冲突 | 读取获准范围、关联证据；用户决定是否成为有效偏好 |
| 个性化推荐 | 本次条件与所选资料范围 | 解释候选、识别需要补充的条件 | 检索与限制过滤；保存推荐依据，用户选择菜谱 |
| 单菜调整 | 具体版本与调整意图 | 提出相关配料和步骤变化 | 执行明确换算、检查关联、生成差异；用户确认后新增版本 |
| 反馈分析 | 用户主动分析已保存反馈 | 建议反馈的适用范围 | 读取原话和版本；长期偏好另经确认 |

首期采用预设阶段的领域工作流 B1，参照 [Building effective agents](https://www.anthropic.com/research/building-effective-agents)的流程编排方式。手机程序控制阶段、权限、预算和确认节点，模型完成阶段内的理解、提取与解释。工具调用经过参数和资料范围检查，计算、版本校验与正式写入由程序执行。缺项或冲突需补充时，保存进度并从对应阶段继续。

#### 工具与接入约定

| 工具 | 最小输入 | 输出与权限 |
| --- | --- | --- |
| `search_recipes` | 检索范围、关键词、筛选条件 | 本资料库内的候选 ID、版本和摘要 |
| `read_recipe` | 菜谱与版本 ID | 配料、步骤、食材状态、来源片段和缺项 |
| `read_preferences` | 本次任务与作用范围 | 有效偏好及证据引用 |
| `read_feedback` | 菜谱／版本 ID | 用户明确保存的反馈与使用记录 |
| `check_constraints` | 候选与明确限制 | 满足、冲突、未知三类结果及原因 |
| `scale_portions` | 原份量、目标份量、确定数量与单位 | 换算结果、规则依据、原始表达和待核对项 |
| `compare_versions` | 基准版本与建议内容 | 配料及步骤差异、关联冲突 |

业务层将工具绑定到当前资料库与授权范围，结果附对象 ID 和修订号。模型引用须对应实际读取的资料，结构化输出通过校验后进入预览与确认流程。

接入验证固定服务、协议与运行环境，在手机上完成“测试连接—读取本地示例—调用 API—执行工具—产生建议—确认写回—再次读取”。记录各步执行位置、出站字段或图片、返回结构及失败处理；服务变更后按新配置复测。

### 7.5 系统架构与运行方式

```mermaid
flowchart TB
    subgraph Phone[手机 App：Android 或 iOS]
        UI[手机界面] --> Biz[端内业务层]
        Biz --> Data[(手机本地资料库)]
        Biz --> Flow[领域工作流与工具]
        Flow --> Data
        Flow <--> Adapter[API 适配层]
        Flow --> Check[结构与依据校验]
        Check --> Draft[结果预览与用户确认]
        Draft --> Biz
        Flow --> State[(本地任务进度)]
    end
    Adapter <-->|用户自有凭据直连| Model[远程模型与识别 API]
    Adapter <-.->|采用托管接入时| Gateway[API 网关：认证与额度控制]
    Gateway <--> Model
```

| 层次 | 职责 | 实现约束 |
| --- | --- | --- |
| 移动端前端 | 展示菜谱、原文、差异、偏好证据和任务状态；收集确认与修改 | 手机内覆盖全部核心操作，保存结果以本地提交为准 |
| 端内业务层 | 资料范围检查、字段校验、版本检查、原子写入和数据管理 | 所有写入经过同一套业务规则，界面通过端内接口调用 |
| 端内工作流与工具 | 组织任务、检索资料、执行计算、调用模型、控制预算和恢复进度 | 任务绑定输入版本、领域资料版本和接入配置，检查点保存在本地 |
| API 适配层 | 转换消息、工具调用与结构化输出，处理连接及模型错误 | 用户凭据使用系统安全存储；每次发送当前任务需要的资料 |
| 手机本地存储 | 保存文字与图片来源、菜谱、标签、版本、反馈、偏好与任务进度 | 数据与附件写入应用私有空间，元数据和文件引用保持一致，可备份恢复 |
| 远程模型／识别服务与可选网关 | 按选定路径提供推理或识别；网关负责认证、额度控制和请求转发 | API 使用加密连接；共享密钥保存在网关，App 使用可发放、限额和撤销的访问凭据 |

前端对应手机界面，业务与数据层在端内实现，可选网关负责远程接入。各设备持有独立资料库，跨设备迁移使用 F08 的备份格式。

#### 移动端开发方案待选

M0 在以下两种方案中选型，并确定框架、语言与最低系统版本。

| 候选方案 | 实现方式 | 重点调研与验证 |
| --- | --- | --- |
| 双平台原生开发 | Android、iOS 分别开发客户端，共用需求、数据格式、领域规则与 API 约定 | 两端实现和维护工作量，行为一致性，系统存储、凭据管理、文件访问与生命周期处理 |
| 跨平台开发 | 使用跨平台方案共享界面或业务代码，按需要接入平台能力 | 框架与插件成熟度，端内工作流、数据库事务和迁移、系统安全存储、文件导入导出及后台恢复 |

两种方案比较同一最小流程：截图入库 → 调用 API 与端内工具 → 确认新版本 → 关闭重开 → 连附件导出恢复。用双平台真机验证能力缺口，记录开发维护成本、构建签名和测试分发条件，据此确定方案与排期。复用组件须满足手机运行和本版数据规则，记录代码版本、许可条件及适配范围。

#### 端内业务接口

界面与工作流共用以下端内业务接口，具体模块名称随开发方案确定。

| 接口组 | 界面或工作流提交 | 端内业务层返回与关键检查 |
| --- | --- | --- |
| 资料导入 | 来源类型、文字／图片／URL | 草稿、来源片段或区域、缺项；检查体积与支持范围 |

错误统一包含原因、用户可执行的下一步和可重试状态。权限错误、版本冲突、输入不支持、上游失败与超时分别显示；前端保留用户已填写内容。

| --- | --- | --- |

| 版本 | 创建后保留，切换默认版本或随菜谱删除 | 反馈与历史推荐引用具体版本；删除后保留删除状态 |

提交时统一检查资料库归属、对象修订号和依据状态。资料删除、修订或偏好撤销后，待采纳结果标为过期，重新运行或校对后再保存。删除同步清理个人内容，保留无内容的操作标识以防旧请求重复写入。

### 7.8 领域定制与软件使用成本的对照

#### 领域定制改善了什么

| 组别 | 配置 | 检验目标 |
| --- | --- | --- |
| B0 通用模型 | 相同模型、任务描述、等价来源、偏好和限制事实，采用普通问答 | 得到通用模型的即时结果基线 |
| B1 领域工作流 | 与 B0 使用相同事实，按预设阶段加入领域提示、结构、检索、规则和工具 | 检验领域定制对结果质量和人工纠正的影响 |

两组固定模型版本、事实、任务、总输入输出预算、最多调用次数和停止条件。图片任务使用同一原图与等价识别能力，B1 检索取得的候选和偏好以等价形式提供给 B0。两组提交相同类型的草稿、理由或差异，按整体方案比较结果质量；领域配置、工具记录与原始输出一并保存。

#### 领域任务与判定

冻结 30 个验收任务：导入 10 个（文字 4 个、截图 4 个、网页 2 个）、偏好及反馈 8 个、推荐 6 个、调整 6 个。至少 10 个源自获准访谈材料，其余由团队编写。样本覆盖正常、缺项、歧义、冲突和失败，对应第 7.4 节的食材状态、用量、收藏动机、偏好范围和撤销规则。开发与验收样本分开，由两名成员预先核对来源、关键字段和允许结果。

每个任务运行 3 次，交错执行并在评分时隐藏组别。人工修正前的三次输出均满足预设条件，任务计为完成；每组报告 30 个任务、90 次运行的结果。有效输入按产出质量判定，预设受限输入按保留已取得内容、说明限制和给出回退方式判定，两类分别报告。

人工纠正按一次字段、依据、范围或步骤修改计数，并记录耗时。每个任务先取三次运行的中位数，再比较双方可完成任务的配对中位数，用于 G1。报告配对数量；失败计入全部任务的完成率分母，数量与耗时单列。

领域结果的关键错误包括：将来源未给出的确定用量标作原文；将已知冲突候选表述为满足限制；将收藏或单菜反馈当作已确认的长期偏好；引用已撤销、已删除依据或错误版本。全部 90 次运行均检查关键错误；数据写入与恢复按第 7.9 节验收。

报告完成率、字段遗漏、无依据新增、偏好范围错误、理由一致性、纠正次数、处理时间与调用成本，并按输入来源和问题类型汇总。

#### 三个代表性对照案例

| 案例 | 统一输入与任务 | 定制后期望检查点 |
| --- | --- | --- |
| D01 缺少用量的导入 | 分别以文字和清晰截图提供“番茄 2 个、鸡蛋 3 个、盐适量”，步骤为“番茄切块、鸡蛋打散，炒蛋盛出，炒番茄后合炒”；份量与时间缺失 | 保留数量和步骤，将份量与时间标为未知；能定位原文或原图；比较校对时间与纠正次数 |
| D02 收藏与口味判断 | 两道辣菜收藏记录、一条“替朋友收藏”的备注，以及用户确认的酸甜偏好；请求分析并推荐 | 收藏特征与本人偏好分开，推荐理由引用酸甜偏好及实际候选 |
| D03 调整后复用 | 2 人份菜谱含某配料 200 克、食用油 10 毫升、盐适量，密度信息缺失；改为 3 人份并记录反馈，之后撤销一项长期偏好 | 分别得到 300 克、15 毫升，盐保留原表达；反馈关联新版本，下次推荐采用更新后的有效偏好 |

#### 对照二：完整软件省下了什么

试用前固定至少 8 位目标用户的名单，分别使用本产品与自己的原有方法，完成“第一轮收集、调整、记录，第二轮找回、继续使用”。原有方法可由收藏夹、相册、笔记和 AI 对话组成，保留实际设置及已有记忆能力。

每人分配两份难度相近的材料，分别用于两种方法；**同一方法的第二轮回到第一轮的菜谱，复用留下的版本与反馈。** 两轮间隔至少 24 小时，平衡工具先后顺序和材料分配，采用同一份任务说明。成员代做记为未独立完成。

记录完成率、耗时、补填与重复输入、放弃原因，单列首次迁移、接入和学习成本。G2 从首次进入 App 计时，包含本次任务所需接入；按指定材料完成导入与校对，配料和步骤可核对才计为保存可用菜谱。G3 比较双方均完成两轮任务的配对样本，报告人数及中位数；第二轮重复填写的每项既有偏好、用量或反馈各计一个条目。全部入组者计入完成率，退出与失败单列。

再从第 3.1 节选择一款功能接近、能实际使用的手机菜谱产品，冻结版本、地区、付费层级和设置，用相同中文材料完成导入、调整、再次使用三个案例。记录人工补救、版本查找与偏好复用步骤；参与者原有方法恰为该产品时可合并记录，结论对应所测案例。

结课按第五节展示两轮使用的变化，附原始材料、操作记录和结果对照。C06 的真实试做另报适口性、改动和再次使用意愿。

| A16／F08、N04 | 菜谱被反馈、推荐和索引引用 | 删除菜谱，再检索、查看日志并运行推荐 | 个人内容及衍生索引清理，相关引用显示删除状态，后续任务停止使用这些资料 |
| A17／F09 | 一份编辑草稿或待采纳建议基于旧修订号 | 在其他页面更新同一菜谱，再提交旧内容 | 提交得到冲突，输入保留；页面读取最新版本，重新确认后才保存 |
| A18／F09、F10 | 智能任务已有本地检查点，API 请求处理中 | 分别切换应用、锁屏、断网和终止进程后重开，选择继续 | 读取已保存进度和预算；未确认的请求状态可见，重复调用由用户决定；已完成步骤和保存操作可识别 |
| A19／F10、N01、N03 | 配置超时、非法结构、工具失败和取消任务 | 分别运行，重试或取消；取消后重开 App 并注入迟到结果 | 正式数据保持一致，失败可解释；取消状态持久保存，迟到结果被丢弃，手工管理可继续 |
| A20／N04、N05 | 越出任务授权范围的对象 ID、含诱导指令的菜谱及私网 URL；采用网关时准备已撤销凭据 | 尝试越界读取、诱导工具调用、抓取受限地址；检查出站字段和已撤销凭据 | 工具与数据访问限定在授权范围；抓取返回拒绝原因，出站内容符合声明，已撤销凭据失效 |
| A21／F01—F10、N01 | 手机已安装 App，备有可用 API 凭据，PC 及局域网服务均关闭 | 仅用手机完成配置、导入、标签整理、偏好确认、推荐、版本调整、反馈与备份恢复 | 全部核心流程可完成；数据与工具操作在手机执行，模型调用经 API 完成 |
| A22／F03、F04、F07—F10、N01 | 手机已有菜谱、历史推荐和待确认建议 | 开启飞行模式，检索编辑、记录反馈、撤销偏好、用本机文件导出恢复并尝试智能任务；联网后继续 | 本地管理与历史结果可用，失效建议被识别；联网任务保存进度并提示网络状态，恢复后按用户操作继续 |
| A23／F02、F08、F10、N03 | 有可用资料库、编辑草稿和待保存结果 | 在保存、导出及恢复时分别注入空间不足或中断，再重开 App | 原库事务完整，恢复已有草稿和进度；导出完成提示与文件实际状态一致，失败原因及处理入口明确 |
| A24／F02、F08、N04 | 一张清晰中文菜谱截图及模糊、裁切、多菜、超限样例 | 手机选择图片、识别校对、保存并备份；异常样例尝试回退 | 有效内容可定位原图，缺项与建议分开；范围内异常保留材料，超限保留文件名与重选入口；发送范围可查看 |
| A25／F01、F05 | 空库及至少 5 份内置家常菜；另有已确认偏好的个人库 | 空库直接浏览并选用示例；在已有库点击推荐，只补一项本次条件 | 空库可开始使用；已有偏好自动读取，本次条件按需填写，候选注明资料范围与依据 |
| A26／F04、F06、F07、F09 | 同一道菜已有原版、个人版和“这次偏咸，下次少放酱油”的单菜反馈 | 保存反馈并重开 App，下一轮找回菜谱、请求调整，再检查其他菜 | 找到当次版本与原话；调整引用该反馈，其他菜继续按自己的有效依据处理；用户可纠正或删除记录 |

**发布阻断项：** 核心操作依赖 PC 或局域网服务；本地数据或来源图片丢失、越出授权范围访问；覆盖原始资料；重复写入；未经确认生效的长期偏好；撤销或删除后仍使用失效依据；已知限制冲突被当作满足；取消、失败或进程中断留下半写入状态。出现任一项，修复并复测相关流程后进入发布。持续集成检查与真机验收分别记录。
