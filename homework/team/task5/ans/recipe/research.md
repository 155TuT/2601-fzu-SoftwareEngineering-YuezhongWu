# 菜谱领域产品调研：个性化的本地菜单管理服务

> 调研更新：2026-10-19。本文为[团队作业选题与需求分析](../task-requirement.md)提供依据，用于明确产品定位、目标用户、领域 Agent 的职责及课程实现范围。
>
> 定位依据来自[QQ 聊天记录整理与截图](assets/research/qq-chat-2026-10-19.md)，外部依据来自[产品官方说明、技术文档与研究论文](assets/research/recipe-research-sources.md)。团队讨论用于澄清产品意图；市场机会、用户收益和技术方案仍需验证。当前尚未完成目标用户访谈、竞品上手对照或原型测试。

## 一、产品定位：让用户逐步拥有适合自己的本地菜单库

### 1.1 核心目标与服务主线

本项目的目标是提供**个性化的本地菜单管理服务**：用户主动选择要导入的菜谱，软件负责保存、整理、检索和管理个人版本；用户接入的 Agent 按团队编写的领域工作流分析这些材料与反馈，在本地沉淀个性化数据，用于口味理解、菜谱推荐和按需提供调整灵感。

用户可以只保存、查找和管理菜谱，也可以主动请求推荐或调整。动态调整是让菜谱随实际生活变化的一种服务，完整排餐、采购与厨房执行可以在管理基础稳定后扩展。

产品主线为：**用户主动导入 → 本地整理与管理 → 口味数据分析与推荐 → 用户按需选择调整 → 反馈沉淀到个人数据与菜谱版本。** 这些能力分别设有入口，用户不必每次走完全部步骤。

为避免“菜单”与“菜谱”混用造成误解，本文约定：

| 概念 | 本文含义 | 在产品中的作用 |
| --- | --- | --- |
| 菜谱 | 一道菜的原料、步骤、来源和相关说明 | 导入、编辑、检索和调整的基本对象 |
| 菜单库／个人菜谱库 | 用户主动收集的菜谱及其分类、个人版本和反馈 | 长期管理与个性化分析的主要对象 |
| 基本菜谱列表 | 产品可提供的少量有来源示例或参考菜谱 | 帮助用户浏览和开始体验，由用户选择是否加入个人库 |
| 一餐菜单／用餐计划 | 某次用餐选定的菜品组合与人数等条件 | 后续可扩展的使用场景 |

聊天提出“也可以有基本的菜谱列表”，并建议参考 Samsung Food（Q16）。因此，可以为初次使用提供参考内容；主要数据仍由用户选择导入和积累。“先填写忌口与喜好，再由系统生成整套菜单”不设为必经流程。

### 1.2 目标用户与首要场景

建议首先研究**有收藏菜谱、实际做饭和反复修改做法习惯的个人，以及负责家庭菜谱整理的人**。他们可能把资料保存在不同内容平台、相册、聊天记录或笔记里，已经有感兴趣的菜，却需要一个能够整理资料、记住个人做法并帮助选择的空间。

首轮用户研究应围绕真实收藏和复做行为选择样本。独居做饭者、两人用餐组织者和长期负责家庭饮食的人可以作为候选，但需分别记录他们的设备、整理意愿和实际困难。用户是否愿意配置自己的 Agent，同样属于需要验证的使用门槛。

一个代表性场景是：

> “把我保存的几道家常菜整理进自己的菜单库。我喜欢酸甜口味，但不确定这些收藏能说明什么。以后想吃点不一样的，帮我从库里挑几道；我选中一道时，再给我一些符合口味的修改灵感。上次做过的改动也要能找回来。”

这是设计与测试示例，不是已经取得的访谈原话。它同时覆盖资料管理、口味理解、推荐和经验积累，用户也可以只完成其中一项。

### 1.3 四项核心服务

**第一，管理用户主动选入的菜谱。** 保存原始来源与内容，整理可核对的字段，支持分类、搜索、编辑和个人版本。导入失败或信息不完整时保留原文及待确认项，让用户可以继续手工整理。

**第二，形成可解释、可纠正的口味认识。** 从用户明确填写的偏好、主动确认的分析结果和做后反馈中积累依据。收藏某道菜只代表用户收集过这份材料，不能直接等同于喜欢其所有食材、口味或做法。

**第三，提供有依据的推荐和调整灵感。** 用户请求时，结合个人库、已确认偏好与本次条件给出少量候选，并说明推荐理由。用户选中一道菜后，可以请求改口味、换材料或调整份量，查看建议与原版差异，再决定是否保存。

**第四，让使用经验回到自己的菜单库。** “这道菜下次少放一点酱油”关联到这道菜；“今天想清淡点”记录为临时条件。反馈、个人版本和长期偏好各有作用范围，用户可以编辑、撤销和导出。

## 二、市场机会与竞品参照

### 2.1 收藏之后的个性化管理

已有产品覆盖菜谱收藏、导入、分类、计划与购物等功能，部分产品也提供 AI 个性化。项目需要验证的机会是：**用户愿不愿意在自己掌握的菜单库中，持续积累个人做法和偏好，并让接入的 Agent 帮助理解、选择和更新这些内容。**

| 待验证的困难 | 用户可能正在做的事 | 本项目应检验的价值 |
| --- | --- | --- |
| 资料分散、再次查找困难 | 在收藏夹、截图和笔记里重复搜索 | 导入与整理是否降低再次找到菜谱的成本 |
| 原始做法与个人改法混在一起 | 靠备注、记忆或多份副本记录改动 | 来源和版本是否帮助用户稳定复用个人做法 |
| 推荐缺少自己的使用上下文 | 反复说明口味，逐条判断哪些菜适合自己 | 可查看、可纠正的偏好是否改善候选质量 |
| 收藏很多，但很少回到个人库 | 浏览新内容，忘记已保存的材料 | 基于个人库的推荐是否帮助重新发现已有菜谱 |
| AI 建议停留在一次对话里 | 把改法、反馈重新复制到其他工具 | 本地工作流是否减少整理劳动，并留下可复用结果 |

### 2.2 成熟产品已经提供的基础

本轮重点复核下列官方资料。表中功能代表文档披露能力，中文处理质量、配置成本和真实使用效果仍待实测。

| 对照对象 | 已公开的相关能力 | 对本项目的比较价值 |
| --- | --- | --- |
| [Samsung Food](https://samsungfood.com/) / [Food+](https://support.samsungfood.com/hc/en-us/articles/32709269852052-What-s-Included-in-Your-Samsung-Food-Subscription) | 收藏菜谱、发现内容、计划与购物；Food+ 提供按偏好调整菜谱等 AI 功能 | 比较收藏、发现、推荐与调整之间的关系，以及用户选择的自由度 |
| [Paprika 3](https://www.paprikaapp.com/windows/) | 菜谱导入、分类检索、个人备注、份量调整、本地存储与离线查看，也提供云同步 | 本地保存和管理已有成熟基线；需证明个性化分析与工作流带来的额外价值 |
| [Recipe Keeper](https://www.recipekeeperonline.com/) | 网页、照片和 PDF 等导入，分类、评分、个人修改、多端同步及离线使用 | 比较导入校对成本、个人版本组织和日常查找体验 |
| [ReciMe](https://www.recime.app/help/en/articles/14773584-why-didn-t-my-recipe-import-correctly) | 从说明文字、音频或原网页导入，提供截图回退；说明私密或登录内容、评论步骤及一帖多菜的限制 | 导入范围必须明确，测试应记录失败和人工修正工作 |
| [Mealie](https://mealie.io/documentation/getting-started/features/) | 菜谱分类、标签、菜谱集、多种导入方式和外部 API 集成 | 可作为管理底座或固定流程基线，比较部署、适配和个性化数据维护成本 |

Paprika 表中固定为 3 版，其 Windows 页面明确说明本地存储和离线查看；中文界面也不等于中文自然语言解析。原调研中的 Paprika 4 Beta、其他内容平台和更多管理产品资料继续保留在[来源索引](assets/research/recipe-research-sources.md)，后续测试时再固定实际版本。

### 2.3 Samsung Food 的具体参考意义

聊天明确提出 Samsung Food，值得优先研究其功能组织。官网把保存个人菜谱、发现新菜、排餐与购物作为相关入口；帮助文档列出链接、电脑扩展、自建菜谱、移动分享和照片等保存方式，同时提醒网页元数据并非全部兼容。[官网](https://samsungfood.com/)、[保存菜谱说明](https://support.samsungfood.com/hc/en-us/articles/18756427379476-How-to-Save-Recipes-to-Your-Samsung-Food-Recipe-Box)

Food+ 的个性化功能允许用户主动选择调整菜谱，并将个性化计划、已有食材检索和烹饪引导列为相关能力。[Food+ 功能说明](https://support.samsungfood.com/hc/en-us/articles/32709269852052-What-s-Included-in-Your-Samsung-Food-Subscription)

由此可以借鉴的产品组织方式是：以能浏览、保存和管理的菜谱为基础，将推荐和调整放在用户需要的位置。基本列表可用于开始体验，个人库承接持续使用，调整建议围绕用户选中的菜展开。这是本项目根据资料作出的设计推论；上述文档没有为本项目证明本地 Agent 接入或长期偏好沉淀的效果。

竞品比较还应包含用户原来的收藏夹、相册、笔记与通用 AI 对话组合。项目的差异需要通过中文材料的整理成本、个人数据可控性、推荐理由和反馈复用来证明。

## 三、领域 Agent：按工作流分析与沉淀个人数据

### 3.1 软件、工作流与用户 Agent 的分工

团队应提供稳定的菜单管理软件、领域资料、工具接口和工作流。用户接入的 Agent 在允许的范围内读取材料，完成提取、分析、解释和建议；保存、检索、版本检查、数值计算等确定性工作由业务程序承担。

| 工作流 | Agent 的职责 | 软件与领域工具的职责 | 用户得到的结果 |
| --- | --- | --- | --- |
| 导入整理 | 理解不规则菜谱表达，识别歧义与缺项，提出分类建议 | 读取用户提交的材料、校验字段、去重提示、保存来源 | 可校对的菜谱草稿 |
| 口味分析 | 结合明确反馈形成偏好候选，指出证据不足或冲突 | 读取获准数据、保存证据与范围、处理确认和撤销 | 可解释、可修改的偏好记录 |
| 个性化推荐 | 根据请求和已确认偏好解释候选，必要时补问 | 在选定菜谱范围中检索、过滤条件、返回来源和版本 | 少量候选及理由 |
| 按需调整 | 针对选中菜谱提供口味、材料或份量调整灵感 | 计算可换算用量、检查相关字段与步骤、比较版本 | 待采纳的修改建议 |
| 反馈沉淀 | 判断反馈适用于这道菜、本次使用还是长期偏好 | 关联实际版本、记录用户决定、更新检索状态 | 下次可以复用和撤销的个人数据 |

工作流规定输入、可用资料、可调用工具、确认节点、失败出口和停止条件。Agent 可以在其中判断是否补问、重检索或提出候选；首期以有限、可检查的流程为实现建议。固定编排与模型动态选路需要在评估中分别描述。[Anthropic：Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)

用户无需为普通的查看、分类、编辑和搜索调用模型。只有请求分析、推荐或调整等能力时，才运行相应工作流。工作流的运行地点、所选 Agent 和实际模型调用路径需要在配置与测试记录中明确。

### 3.2 一次完整使用如何积累价值

以下过程展示同一份个人菜单库如何被持续使用，各步骤可以分次发生。

1. **自主导入。** 用户选择一份文字菜谱或受支持网页，也可以从基本列表选入一份。软件保留来源与原始内容，Agent 整理字段，缺失用量保持未知；用户校对后保存。
2. **形成可用的个人库。** 用户分类、搜索、补充自己的备注。查看或保存菜谱不要求先填写完整画像，也不自动启动一餐计划。
3. **分析与确认偏好。** 用户请求分析自己的收藏和反馈。Agent 给出带依据的候选认识；只有收藏而没有明确评价时，应说明证据有限。用户可以确认“喜欢酸甜”，或纠正“这几道辣菜是替朋友收藏的”。
4. **按需获得推荐。** 用户说“从我的菜谱里找几道符合口味、最近没做过的”。系统读取已确认偏好和有记录的使用情况，解释推荐理由。缺少做饭记录时说明未知，不能把未记录解释为从未做过。
5. **给一道菜提供调整灵感。** 用户选中菜谱并提出要求。Agent 给出建议及涉及的配料、步骤变化，用户选择保留原版、仅本次尝试，或另存为个人版本。建议不会直接覆盖原始资料。
6. **保存与复用反馈。** 用户记录实际改动和体验，确认其中哪些可以长期应用。后续推荐引用这些记录，用户撤销偏好后停止使用相关依据，已有菜谱版本仍保留自身历史。

人数、食材或用餐成员变化可以作为第 4、5 步的条件，但不是启动服务的必要事件。用户只请求整理、查找或推荐时，系统应完成该请求并停止。

### 3.3 口味与记忆需要保存什么

建议把“材料里出现的信息”和“对用户的判断”分别保存，避免从收藏内容直接生成确定的个人画像。

| 数据对象 | 例子 | 保存与使用规则 |
| --- | --- | --- |
| 原始材料 | 某菜谱使用辣椒 | 描述菜谱本身，不自动成为用户喜好 |
| 偏好候选 | 从几次反馈推测可能偏好酸甜 | 保留证据和待确认状态；明确标示推测 |
| 已确认偏好 | 用户确认喜欢酸甜口味 | 记录适用对象、来源、更新时间，支持修正和撤销 |
| 单菜改法 | 这道菜下次少放酱油 | 关联菜谱与具体版本，不自动推广到所有菜 |
| 临时条件 | 今天想清淡一点 | 仅用于当前请求，需长期保存时再由用户确认 |
| 使用与反馈记录 | 某次采用哪个版本、结果如何 | 记录实际选择与反馈，不能由点击或收藏推断已经做过 |

建议以“来源—菜谱—个人版本—反馈”为基本关系，再通过有证据的偏好记录支持推荐。推荐记录保存本次使用的候选、版本和偏好依据，便于解释和检查。若未来加入一餐计划，再让计划引用具体菜谱版本。

个人数据至少应支持查看、编辑、导出和删除；撤销某项偏好后，后续推荐与分析不再把它作为有效依据。冲突反馈应先保留上下文，避免用一次临时评价覆盖长期设置。

### 3.4 领域知识如何进入工作流

| 领域知识 | 主要作用 | 需要保留的边界 |
| --- | --- | --- |
| 菜谱结构、来源与字段含义 | 整理配料、步骤、份量和时间 | 原文缺失与模型建议分开，来源可核对 |
| 食材名称、别名和状态 | 检索、分类、解释候选与检查材料冲突 | 生熟、干湿等状态分开，不确定名称保留原文 |
| 口味、做法与反馈表达 | 理解“偏咸”“想清爽一点”等描述 | 菜谱特征、临时条件和长期偏好分别处理 |
| 用量、单位与产量 | 调整份量和比较个人版本 | “适量”“一把”等保留语义，缺乏依据时不补造克数 |
| 原料用途与步骤关联 | 检查替换材料后哪些步骤也需要修改 | 建议说明依据与未知项，真实口味需实际反馈 |
| 用户明确限制 | 过滤候选，检查调整方案 | 信息不足时提示核对，不能把未知当作满足条件 |

[Schema.org Recipe](https://schema.org/Recipe)可为菜谱、配料、步骤、份量和时间字段提供结构参照，导入仍需核对原始内容。[SHARE](https://aclanthology.org/2022.emnlp-main.761/)研究配料变化与做法修订的关联，可用于设计调整工作流的检查项；它不能证明本项目的修改建议符合真实口味。

首期聚焦日常菜单管理、偏好理解与做法灵感。聊天开头提到的疾病、生理期等属于提问举例，未被确认为必须实现的服务；精细营养计算和疾病饮食建议不进入课程核心范围。

## 四、本地运行、Agent 接入与移动／PC 使用

### 4.1 把“本地”落实为可检查的方案

聊天明确了本地工作流与个性化数据沉淀方向，尚未指定部署形式或模型。下面是实现建议，需在原型中验证后写入正式需求。

| 层次 | 首期建议 | 需要验证的内容 |
| --- | --- | --- |
| 数据保存 | 个人菜谱、版本、偏好和反馈由用户侧本地数据存储管理 | 重启后持久化、导入导出、备份恢复和删除是否有效 |
| 工作流执行 | 在用户侧运行工作流与受控工具，调用用户配置或接入的 Agent | 能否按约定读数据、返回结构化结果、展示差异并保存确认结果 |
| 模型推理 | 按实际接入方式使用模型；本地模型或远程 API 分别说明 | 接入能力、延迟、调用成本及实际传出的字段 |
| 跨设备访问 | 明确选定一条移动端连接或同步路径 | 连接条件、授权、版本冲突、服务不可达与未同步提示 |

本地保存数据、本地编排工作流和本地模型推理是三个不同层次。若接入远程模型，工作流仍可能向服务提供方发送选中的菜谱片段与必要偏好，界面与文档应说明实际传输范围。只有逐段验证链路后，才能描述具体的离线能力。

### 4.2 软件与接入方案

建议以响应式界面配合本地管理服务作为首期候选：前端提供菜谱库、来源对照、分类检索、偏好查看、候选推荐、版本差异和反馈入口；本地服务负责数据、版本与领域工具；Agent 适配层连接一种经过验证的用户 Agent／模型接入方式，运行团队提供的工作流。

首期应先验证一次真实的接入链路：**读取用户选定材料 → 调用工作流与领域工具 → 返回带依据的结果 → 用户确认 → 写回本地数据 → 再次读取并复用。** 支持的 Agent、模型接口、运行环境和配置步骤以实测清单为准，暂不承诺任意 Agent 均可兼容。

软件维护来源、状态和最终保存规则。导入材料作为待处理数据，不能改变工具权限或写入规则；Agent 返回的字段须经过校验。模型超时、工具失败或接入未完成时，已保存菜谱和手工管理仍可使用，失败任务不得留下半写入的偏好或版本。

Mealie 的分类、导入和 API 可以作为集成试验或基线，但是否适合承载所需的个人版本、偏好证据和接入方式，应通过原型验证，再结合具体版本与许可决定复用范围。[Mealie 功能文档](https://mealie.io/documentation/getting-started/features/)

### 4.3 两端入口与同步边界

| 能力 | 移动端重点 | PC 端重点 |
| --- | --- | --- |
| 收集与管理 | 粘贴文字或链接、快速查看和选择菜谱 | 对照来源校对、整理分类、比较个人版本 |
| 个性化推荐 | 简短表达需求、浏览少量候选与理由 | 审阅偏好依据、处理冲突和比较候选 |
| 调整与反馈 | 对选中菜谱提出改法、随手记录体验 | 比较配料与步骤差异、整理长期经验 |
| 个人数据与接入 | 查看连接和同步状态、修改明确偏好 | 配置本地服务与 Agent、导入导出和维护资料 |

两端访问同一资料需要明确的连接或同步实现。首期可以验证手机在授权网络中访问用户侧本地服务的路径；服务未运行或手机离开可达网络时，应明确说明功能受限。远程同步、移动端独立离线副本和复杂冲突合并按后续需求另行评估。

本地软件连接属于接入方案的一部分，与后续厨电、传感器等硬件联动分别评估。PWA 缓存可以用于改善已保存内容的访问，但浏览器管理后台生命周期，不能仅凭网页形态承诺持续运行 Agent。[MDN：离线与后台运行](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)

## 五、课程实现范围：先完成个人菜单管理闭环

### 5.1 核心范围与扩展

建议优先完成：**导入或选入菜谱 → 本地管理与检索 → 确认个性化依据 → 按请求推荐 → 按需调整并保留版本 → 反馈可复用、可撤销。** 普通管理能力和 Agent 工作流共同组成完整软件。

| 范围 | 内容 | 验证重点 |
| --- | --- | --- |
| 课程核心 | 手工／文字导入、少量受支持网页、来源与缺项校对 | 用户能把自己的材料整理进菜单库 |
| 课程核心 | 本地持久化、分类检索、编辑、个人版本、导出和删除 | 数据可管理、可找回，原版与个人改动可区分 |
| 课程核心 | 一种可运行的 Agent 接入方式及领域工作流 | 能完成分析、工具调用和确认后写回，配置成本可记录 |
| 课程核心 | 有依据的口味分析、偏好确认与个性化推荐 | 收藏不直接等同喜好，推荐能解释并接受纠正 |
| 课程核心 | 用户触发的单菜调整、版本比较、反馈与记忆撤销 | 采纳与否由用户决定，经验可持续复用 |
| 课程核心 | 移动与 PC 界面、明确的连接方式、异常恢复 | 实际支持范围可检验，未连接时不显示虚假同步结果 |
| 课程核心 | 上线演示、访问地址、测试方式和定制效果对照 | 老师和同学能检查软件与 Agent 的真实能力 |
| 体验辅助 | 少量自写或有权使用的基本菜谱列表 | 无私人数据时可浏览和尝试，加入个人库由用户选择 |
| 软件扩展 | 图片导入、一餐或周计划、购物清单、厨房步骤模式、家庭多账号与语音 | 依据真实用户需求和核心完成度再决定 |
| 后续研究 | 厨房显示、按钮、语音终端、传感器与厨电接口 | 不纳入本次实现与验收 |

临时来客、采购缺料和多菜并行仍可保留为后续场景材料。首期验收应优先检查菜谱与个性化数据能否被长期管理和复用，再衡量是否增加整餐调度。

### 5.2 本地使用与课程上线如何同时检查

课程要求最终软件上线并提供访问地址。本地产品形态仍需准备可访问的演示实例，以自写或授权样例展示同一套管理界面与工作流，并提供必要测试方式；演示实例与用户私人菜单库的数据边界须明确。

同时提供可复现的本地运行说明和检查步骤，实际演示本地持久化、Agent 接入、结果写回与再次读取。在线演示证明软件可以访问，本地测试证明本地能力；两项证据分别记录。若在线使用共享演示模型，应标明其配置与用户自接 Agent 的差异，不把云端演示当作本地运行证明。

首轮原型需要优先回答三项问题：用户配置 Agent 的成本是否可接受；手机连接本地服务能否满足主要场景；核心数据能否在模型服务不可用时继续手工管理。结果将决定正式技术选型和移动端范围。

## 六、验证方法与作业交付

### 6.1 先取得真实使用证据

第一轮可从 8—12 位有收藏和做饭经历的用户开始，这是探索性工作量建议。请对方展示最近保存、找回、修改和再次使用的一份菜谱，记录材料位置、个人改法、口味判断及重复整理的过程。

访谈重点包括：为什么保存这份菜谱，收藏是否等于想吃，实际做过哪些改动，之后能否找回，什么时候需要推荐，愿意让系统记住哪些信息，以及是否愿意配置本地服务或 Agent。把用户展示的行为、原话与团队解释分别记录。

QQ 记录解决的是团队定位表述，不能计入这些目标用户访谈。后续应让参与者用原有方法、一个匹配的成熟产品和本项目原型完成相近任务，同时记录迁移、配置与学习成本。

### 6.2 分开验证领域定制、数据沉淀与动态判断

| 比较组 | 提供的条件 | 回答的问题 |
| --- | --- | --- |
| B0：通用模型问答 | 相同模型、等价菜谱材料与偏好事实，无专用领域工具 | 普通对话能够完成到什么程度 |
| B1：领域工作流 | 相同材料与模型，加入结构化字段、检索、规则、确认与保存工具 | 领域定制和持续管理带来什么收益 |
| B2：允许有限动态选路的 Agent | 与 B1 相同数据、工具和预算，可根据结果补问、重检索或修订 | 动态判断是否进一步减少错误或人工操作 |

首期应先验证 B0 与已实现的领域工作流；若实现了动态选路，再加入 B2。按预设流程完成分析和工具调用可以作为领域定制成果，描述时据实说明编排方式。

比较即时结果质量时，各组收到等价来源、用户限制和偏好信息；比较长期数据复用时，另行记录提供上下文、手工整理与重复输入的工作量。固定输入、模型版本、可用资料、预算与停止条件，避免把额外信息误计为 Agent 能力提升。

开发样本与冻结验收样本分开，两位成员核对关键字段、来源与预期条件。当前未完成这些测试，不预填准确率、推荐接受率或节省时间。

### 6.3 代表性验收任务

| 代表任务 | 应检查的结果 |
| --- | --- |
| 未导入私人菜谱时进入软件 | 可以浏览基本列表或直接手工录入；不强制生成菜单、建立完整画像 |
| 导入一份用量不完整的菜谱 | 来源和缺项可见，没有把模型补充当原文；用户可校对并保存 |
| 重新打开本地菜单库，搜索并编辑菜谱 | 已保存内容持久存在，分类和检索有效，个人修改可追溯 |
| 分析含有“替朋友收藏”的菜谱与明确口味反馈 | 收藏与本人喜好分开；候选偏好有证据，冲突和不确定性可见 |
| 从个人库请求推荐 | 候选来自所选范围，理由对应有效偏好；信息不足可补问或返回普通候选 |
| 只请求给一道菜提供修改灵感 | 返回相关改动与依据；保留原版，用户可以不采纳或另存版本 |
| 记录单菜反馈与临时要求，再进行下一次推荐 | 数据归属和范围正确，临时条件不无故变成长期偏好 |
| 撤销偏好或删除个人记录 | 后续检索、推荐和分析停止使用失效内容，历史版本的处理符合说明 |
| PC 保存后通过支持的手机连接方式查看 | 两端读取已确认版本，连接失败、冲突或未同步状态明确可见 |
| Agent 未连接、模型失败或工具返回错误 | 手工管理仍可继续，已有数据保留，不写入未完成的分析结果 |
| 导出并在声明支持的环境中恢复数据 | 菜谱、来源、个人版本和偏好范围按实际支持格式保留 |

指标应包括关键字段错误、无依据新增、偏好误判、推荐理由一致性、用户采纳与纠正次数、重复输入量、任务完成率、配置时间、处理耗时和调用成本。无依据写入关键字段、未经确认保存长期偏好、撤销后继续应用等，可设为冻结样本中的重点阻断项；同时报告完成率，避免靠拒绝任务掩盖问题。

推荐是否有帮助、调整是否合口味，需要用户实际选择与反馈；保存、版本、撤销和持久化是否正确，由程序与人工核对。长期使用、减少浪费或健康收益需要另外的跟踪研究。

## 七、后续演进：排餐与厨房设备

在菜单管理和个性化工作流得到验证后，可以研究一餐／周计划、购物清单和厨房步骤视图。此时计划引用用户确认的菜谱版本，人数或材料变化触发局部修订，已购事实、手工清单项和实际执行进度需保留。

更后续的设备方向包括显示当前菜谱、语音查询、按钮记录进度，以及读取带时间和单位的传感器数据。已有的 Home Assistant、MQTT、小智 ESP32 与 Home Connect 资料保留在[来源索引](assets/research/recipe-research-sources.md)，作为独立可行性研究入口。

设备接入需要逐项确认接口、身份、授权、动作能力和失联处理；本地软件运行不会自动赋予厨电控制能力。设备联调、网关、硬件采购和硬件验收不属于本次课程核心。后续扩展仍应服务于用户已选择的菜谱和个人数据，避免让附加功能取代菜单管理目标。
