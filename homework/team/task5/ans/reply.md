# 对老师课上指导的反思

## 课上老师对大家答辩的反馈

- 所有的基于 Agent 的软件都要回答一个问题：为什么不直接用大模型，而用你们的软件？
- 对需求的分析还不够深入：发现问题但没有发掘问题发生的原因，也就无法找到具有针对性的方法。
- 大家现在更像一个 harness tool，一套 skills + prompt + RAG。希望能从实际问题出发，更能体现软件工程的价值。

## 博客园中作业要求的相关部分

### 作业描述

近年来，智能体技术迅速发展，在智能聊天机器人、自动化系统等领域得到广泛应用，逐渐改变着人们的工作和生活方式。智能体不仅可以提供对话服务，还可以结合工具、软件功能和硬件设备，为用户带来更具互动性和实用性的体验。

本次团队项目要求大家 **自主选择一个领域** ，围绕用户的真实需求和领域知识，构建对应领域的专业化智能体，并在此基础上构建一个完整的软件。应明确服务对象、使用场景。

领域知识是指完成某一领域具体任务所需的专业概念、规则、标准、案例和业务流程。例如：

- **医学领域——医学检验知识学习软件：** 面向正在学习血常规检验知识的医学生，整理教材中红细胞、白细胞、血红蛋白等指标的含义、相关知识点及教学例题。智能体根据这些资料解释术语、生成练习并分析错题，注明教材出处；软件提供知识查询、练习作答和学习记录等功能。
- **金融领域——企业财报阅读软件：** 面向初学财报分析的财会学生，整理资产负债表的科目含义、流动比率等指标的计算规则，并选取公开财报作为示例。智能体从财报中提取相关数据，调用计算工具计算指标，解释计算过程并标明数据出处；软件提供财报导入、指标查看和分析记录等功能。

团队应根据目标用户的真实需求，选择与具体任务相关的领域知识，构建对应的智能体，并在此基础上开发功能完整、能够实际使用的软件。

以上仅用于说明“领域知识”的含义，不限制团队的选题方向。

团队可以通过领域资料整理、提示词设计、知识检索、工具调用或流程编排等方式，对通用模型进行领域定制，使智能体在所选领域表现出更好的针对性和实用性。可以选择纯软件应用，也可以探索智能体与硬件设备的联动。

### 项目目标

1. **领域不限，以领域 Agent 的构建为核心。** 团队应根据真实需求确定一个具体任务范围，说明智能体需要哪些领域知识、如何使用工具或组织任务流程，并展示其能够完成的代表性任务。应通过典型案例对比定制前后的表现，说明能力提升体现在哪里。
2. **模型和智能体平台不限。** 可以选用 GPT、Claude、文心一言、Kimi 等模型或相关智能体平台。实现的智能体应能够通过 API、SDK 等方式与团队开发的软件系统集成。
3. **软件形式不限。** 可以是小程序、APP、WEB 网站、桌面软件、系统、游戏等。智能体与硬件实现有效联动可获得额外加分，例如利用传感器采集数据、通过显示屏或语音设备交互、控制简单物联网设备。硬件联动属于可选拓展，不是必做要求，加分规则见下方“激励与评奖机制”。开源硬件案例可参考：[小智 AI（xiaozhi-esp32）](https://github.com/78/xiaozhi-esp32)。
4. 所有应用最终需要 **上线运行** ，提供访问地址及必要的测试方式，供老师、助教和其他同学检查。涉及硬件的项目还需说明联动效果的演示与检查方式。
5. **自主选题，选题要真实、可用、有价值、有情怀。** 需求应来自真实调研，说明目标用户、使用场景和要解决的问题。
6. 本次作业需在 **课上答辩** 并 **撰写博客** 。注意答辩与博客提交截止时间，两者分别安排，请注意下方的时间要求。
7. 不符合要求的选题将被要求修改或重新选题，并在下一次课上进行答辩。

## 对老师课上意见的思考和回复

在这里，我想针对老师提出的第一条和第三条意见给出我的判断：**领域知识、工具和工作流既然可以作为模块、插件或通过MCP、CLI等方式接入通用 Agent，那么作业就应该允许我们复用成熟底座，而把工作放在领域定制和软件交付上。“面向领域的专业化能力”这个命题本身并不能证明重新搭建一套 Agent 的必要性。**

或许我们可以先看看现在的一些专业软件和曾经的领域 Agent 在怎么做：

- **ComfyUI** 的官方 CLI 可以运行工作流、返回结构化结果，并提供供 Agent 使用的 skills。专业的生成流程可以继续由 ComfyUI 执行，通用 Agent 负责调用与组合。[官方仓库](https://github.com/Comfy-Org/comfy-cli)
- **OpenDesign** 直接复用现有 Coding Agent 作为执行引擎，同时通过 skills、CLI 和 MCP 开放设计能力。设计系统、模板、工作流和工作区构成了它的专业性。[官方仓库](https://github.com/nexu-io/open-design)
- **Figma** 通过 MCP 提供设计上下文和原生画布读写能力，再通过 skills 组织具体操作。外部 Agent 可以使用专业设计工具，成果仍然保留为可编辑的设计文档。[官方文档](https://developers.figma.com/docs/figma-mcp-server/)
- **GitHub Copilot** 的 SDK 允许用提示词、工具范围和 MCP 服务定义专业 Agent，并交给同一个运行时调度。专业角色与通用底座，本来就可以在同一套系统里组合。[官方文档](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/custom-agents)

这些已经存在的产品支持的是一条很具体的路线：**通用底座加领域模块。** 领域知识、工具和流程可以独立维护，用户界面可以按实际任务设计，执行循环则复用成熟实现，而独立 App 或网页也完全可以采用这套架构。

领域工作的价值，至少在我看来，恰恰就落在这些具体能力上。它们能够被通用 Agent 集成，也恰好说明成果可以复用。至于是否需要自建底座，则应当考虑：现有运行时缺了什么？重新开发以后，任务结果、部署条件或运行成本又改善多少？

所以，我真的很想知道，老师所认可的“领域 Agent”究竟指什么。如果是针对领域任务组织知识、工具和流程，上述方案已经在做；如果还要求一套独立的执行循环，就应当说明这个额外要求解决了什么问题。

------

再看这门课的现实条件：我们只有六周。从我接触的同学来看，多数人只学过基础代码语法，工程、设计和大模型原理都还需要补齐。与此同时，大家还要完成调研、需求分析、协作开发、测试和上线。 **在这样的起点和期限下，很难指望多数同学掌握后训练或微调，并证明它带来了可靠的领域收益。** 运行一遍教程、得到一个权重文件，与能够解释数据选择、排查训练问题、验证效果并完成部署，相差很远。把这部分交给少数有经验的成员，也仍然要回答其他成员学到了什么。课程如果期待这个层次的成果，就需要对应的先修知识、数据、算力和评估支持。

在这样的条件下，同学们显见的无法掌握对模型的后训练和微调，也就是说我们本来就是在相同的基模下拓展所谓的“软件能力”。在这种情况下，要想在某个领域做出比通用 Agent 更好的效果，我们能做的有什么呢？显然对多数同学来说，更现实的工作正是：

- 整理可信的领域资料，建立可检查的检索与引用方式；
- 把领域规则和常用操作做成工具、工作流与 skills；
- 设计任务指令、示例和上下文组织方式，再用实际任务验证效果。

把这些工作做好后，还要进入软件：保存状态，处理异常，让用户能够检查、修正和继续使用结果。六周内只把这条流程做完整，都已有足够多的软件工程问题需要学习。

就比如，其实给模型的首轮提示词都值得认真设计：DeepSeek V4 Pro [正式版公告](https://api-docs.deepseek.com/zh-cn/news/news260813/)就曾明确说明其公开 Code Agent 基准使用 V4-Pro-0813 与 dsh 极简模式。社区随后对首轮工具配置做了实验，观察到“We”和“Let me”等推理文本风格的变化；后续独立复测支持这种风格差异，虽然能力增益的幅度与稳定性仍待确定，但已是值得研究的问题：提供相关领域的初始轮对话引导，复现优秀的首轮system prompt和模型响应，是否有助于提高模型在对应方向上的表现？（相关[配置实验](https://github.com/xiaobright/dsh-anchored-standard/issues/11)、[独立复测](https://github.com/xiaobright/dsh-anchored-standard/issues/65)）

因此，首轮提示、工具定义和上下文组织应当作为可以设计、测试和调整的工程变量。它们有没有用，要看的是任务结果，而不是因为架构 “更像 harness tool，一套 skills + prompt + RAG” 就判断工作没有价值，这也是老师第三条反馈让我困惑的地方：作业明确允许“领域资料整理、提示词设计、知识检索、工具调用或流程编排”，评分要求还写了“所选方案是否适合团队能力”。那么第三个问题究竟是在指出哪一项缺陷？

如果是用户问题没有分析清楚、软件流程没有完成、定制效果缺少证据，就应当如您所提出的问题二一样具体指出这些问题。但如果技术构成本身就是被否定的理由，那作业允许的方法为什么又成了否定项目的依据？**学生又需要把这些方法用到什么程度，才算完成了老师所说的“领域 Agent”？**

------

此外，“为什么不直接使用大模型”当然值得回答，但比较对象也应说清楚：模型聊天界面、能够调用工具的通用 Agent、已经接入等价领域模块的通用 Agent，这三者提供的能力并不一样，而评价或许可以具体落在这三个问题上：

1. **领域定制改善了什么？** 用同一模型比较直接处理原始资料与使用领域模块的表现，记录任务成功率、错误和人工修正。
2. **独立软件方便了什么？** 与接入等价模块的通用 Agent 比较，检查操作、状态保存、结果核对和持续使用的成本。
3. **所选实现适合这个任务吗？** 如果固定流程已经足够，增加动态 Agent 带来了什么收益？如果成熟底座已经够用，自建又改善了什么？

这些问题都可以用代表性任务回答，自然也应当允许最后得到“复用现有底座更合适”的结论。选择合适的架构、控制实现范围、验证真实收益，**本来就应该属于软件工程能力**。

作业要求中还有一个需要讲清楚的地方：一方面要求从真实问题出发，另一方面又预先要求所有项目“以领域 Agent 的构建为核心”。需求分析可能发现，一个固定流程或普通软件功能就能把问题解决。课程如果是为了练习 Agent 集成而限定技术路线，就把这个教学约束说清楚，再指导大家选择适合的任务；如果要求技术方案由需求推出，也应该允许分析结果影响和更改最终方案。

因此我想问的其实很简单：**在六周的课程里，面向同学们的能力起点，领域知识、工具、流程和完整软件需要做到什么程度？如果的确证明复用通用 Agent 底座、经外接一套 skills + prompt + RAG 即可解决实际问题的话，方案本身为什么会是需要改进的问题？**

------

我真的太想知道老师所构想，或所认可的“领域 Agent”到底有什么这些方法之外的手段，以至独特到是通用 Agent 一定无法做到的。或者，我们可以先不谈 Agent 这么工程化、目前在我看来也十分泡沫的方向，来聊聊模型界已经发生的事情：

- **视觉基础模型正在改写 CV 中逐任务造模型的分工。**
  - [DINOv3](https://ai.meta.com/research/publications/dinov3/) 展示了统一视觉骨干在多种下游任务上的迁移能力；
  - [SAM 3](https://github.com/facebookresearch/sam3) 则把图像与视频中的检测、分割和跟踪纳入同一个可提示的模型，支持文本和视觉提示。
  - 这股变化由视觉自监督、视觉语言建模等路线共同推进。原本分头打磨的任务可以共享底座，再针对任务适配。基础模型正在挤压逐任务重新训练的空间：换一个任务名称，究竟还剩多少必须从头造轮子的理由？
- **领域模型的优越性应在相同条件下论证。**
  - 2026 年 9 月的一项[医学术语预印本](https://arxiv.org/html/2609.13556v1)中，Llama-3.1-8B-Instruct 在术语理解、识别两项任务上的准确率，都高于同底座的医学微调版本 UltraMedical。
  - 同月的[天文学预印本](https://arxiv.org/html/2609.17644v1)，在共同的 204 道纯文本题、模型裁判评分下，GPT-5.5、Sonnet 4.6 等通用模型超过了所测天文学模型；AstroSage 70B 同时又超过了 Llama 3.1 70B Instruct。
  - 医学图像也给出了另一方向的结果：2026 年 5 月的[MedGemma 1.5 报告](https://arxiv.org/html/2604.05081v2)中，在其评测设置下，MedGemma 1.5 4B 的 MedQA 文字问答准确率为 69.1%，Gemini 3 Flash、Pro 分别为 94.3%、95.1%；换到 PathMCQA 病理图像选择题，三者则分别为 70.0%、59.3%、59.1%。
  - 专业化的确可以提高任务质量，但更强的通用模型基线也可以把差距重新拉开。究竟强在哪里，要把任务、版本和评测设置摆出来，而下一代模型来了也仍需要重新比较。仅凭模型前的“专业”二字是没办法直接替结果作保的。

大语言模型通过优化参数、学习数据的过程中沉淀下来的是模式、关系和知识，这些人类至今难以穷尽的潜变量。其学习这些领域知识也并不会像跷跷板一样，学了理科就文科差（更何况还有 MoE 这些方向的努力），而是更加全方位的能力提升：我们本来就是在用全人类的语料大炼钢铁，只是过去较为封闭的领域熔炼的稍慢一点而已。

无数的研究已经证明：领域专用模型相较顶尖通用模型只剩下了成本和小规模优势。更何况各家的非旗舰通用 flash 模型也正在以同样恐怖的蒸馏、学习和发展速度来追赶顶尖通用模型的能力。其实在我看来这是模型本身的架构导致的必然结果：AI 的训练方式就是堆参数寻找模式和结构，而不是用领域知识来堆对某特定领域的拟合程度。只喂特定领域的知识不仅会出现严重的边际效应，甚至可能会出现难以察觉其他领域交叉知识中相似结构的逻辑倒退。

既然通用模型会继续抬高领域方案的门槛已是可预见的未来，那么领域模型就该说明自己在具体任务的质量、成本和部署条件上赢在哪里，这些收益又能否随模型迭代继续成立。而 Agent 又何尝不是这个道理呢？

通用 Agent 本来就是作为人类与 AI 模型协作的工作流范式而出现的，凭什么到特定领域使用相应工具，就会不如重复造一个专用 Agent 的效果呢？哪个领域是不需要和通用 Agent 的工作流一样讲逻辑、讲协作、讲规范、讲专业的吗？而我们所做的相关领域的工作流程，不该是为了整合和供通用 Agent 理解并调用而存在的吗？看到那些数学建模 Agent、社科 Agent，还有要求中所举的例子，我是真的很想知道有哪些领域的工作流是会有必要重新造一遍轮子的。

其实从这个角度来说，DeepSeek Harness 的理念还真是面向未来的：一切都只是供日益强大的模型自主探索的插件罢了。

## 对自己项目的反思

我深切同意老师第二条问题的提出：我们组的项目在这两周内的确没有做到真实目标群体的调查、访谈和意见沉淀，这切实导致了我在答辩时无法回应老师对菜谱类软件真实需求的疑虑，而我也已在答辩前就明确在ppt中指出了这点缺陷，并将在后续补齐。

但我同样认为，我们组的方案其实是很贴合您**以领域 Agent 的构建为核心，选题要真实、可用、有价值、有情怀**的作业要求的：

- 首先是您所指出的**菜谱类软件的复杂输入**，我想，接入大模型恰恰就是为了补齐这一能力缺陷的：菜谱来源可以是语音讲述转文字、按短视频链接导入、识图、按搜索进行模糊匹配，这些全都匹配上了 Agent 已有的能够代人完成繁琐工作的多模态和语义识别与理解能力，自然也是我们所期望解决的**原有竞品的痛点之一**。
- 然后是**真实用户群体问题**，这里我实在疑惑：我当然知道您这种生活中已然熟练的厨师**现阶段**并不需要参照菜谱，但这不也恰恰说明了当下的您也并不是菜谱软件的目标用户吗？我在课上所说的“我们主要做了成熟而广泛的竞品分析”的含义是：因为存在相同领域的直接大厂竞品，因此我们的目标是对标其闭源版本做出开源版本，并借助 Agent **优化已有的痛点**。而需要菜谱的人群就至少存在这样几类：
    1. 刚刚步入脱离家庭的独立生活，需要菜谱指导做菜的年轻人
    2. 需要借助菜谱这一固定计划的形式，在不熟练的做菜流程中获取安心感的所有不熟练者（通常为家庭中不常做饭的一位）
    3. 需要传承自己菜品做法的家中长辈或厨师
- 接下来则是**痛点**问题，菜谱作为**较稳定的**菜品传播媒介，痛点也最起码是存在**个性化**问题的：
  - 面对一个新菜谱，倘若第一次就不合口味，后续或许难以继续尝试，是否会违背和打击用户搜集并烹饪新菜谱的热情和耐心呢？
  - 倘若想根据心仪菜谱、已有食材和特殊要求（生病忌口、健身需要等）而改良为合心意的口味版本，对目标用户群体是否要求过高呢？
